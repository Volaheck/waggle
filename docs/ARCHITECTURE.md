# Architecture

```
Telegram ──polling/webhook──▶ bot (grammY) ──▶ PostgreSQL
                                  │                 ▲
                         Mini App API (Hono) ───────┤
                                  │                 │
                     scheduler ── chronicler (Claude, every N hours)
                                └ weekly card clean-up (Claude)
```

One Node.js process runs the bot, the HTTP API for the Mini App and the scheduler. PostgreSQL holds everything; migrations live in `migrations/` and run on start. `003_memory.sql` adds the bot's memory: its own messages and the forum topic of every message (`messages.from_bot`, `messages.thread_id`), aliases, private notes, debates in the chronicle, and the log and per-chat switch of its interjections (`interjections`, `chats.interjections`).

On stop the chronicler starts no new call, and the process keeps serving until the call under way finishes (up to 40 s; after that it is cancelled, and what it cost so far still counts towards the budget), then closes. Batches that were already applied stay; a pass cut off by the stop or by a crash is marked failed and continues after the usual back-off. In webhook mode an update that fails goes to the same error handler as in long polling, and Telegram always gets 200, so it never delivers the update again.

## Chats

The bot serves any number of group chats (`chats`). A new chat is `pending` until a bot owner approves it; a chat added by an owner is approved at once. Messages from chats that are not approved are neither stored nor processed, and a rejected chat is left (and stays rejected). Owners are exactly the IDs in `ADMIN_TG_IDS`: removing one revokes that person's rights at the next start.

When a basic group becomes a supergroup, Telegram gives it a new id. The chat's approval and everything stored about it move to the new id in one transaction (`src/core/chat-migration.ts`), whichever of the two announcements arrives first. The supergroup numbers its messages from 1 again, so the old messages keep their order below zero and get no t.me link.

Everything the bot knows is scoped by `chat_id`: messages, facts, rejected facts, aliases, private notes, projects, chronicle, extraction runs, the interjection log and LLM spending. A supergroup upgrade carries the interjection switch (an owner's "off" on either id wins) and the log, so the gap and the daily cap go on counting. A Telegram account is one `users` row; its presence in a chat is a `members` row (tagline, opt-out, activity), so the same person has an independent card in each chat. Data imported before a chat existed carries `chat_id = 0` until an owner attaches it to a chat (`/chats`).

In DM the bot asks which chat to show when the person is in several and remembers it (`users.current_chat_id`). Links into DM and the Mini App carry the chat as `c<id>` (start parameters allow only `[A-Za-z0-9_-]`), e.g. `?start=c100123_me` or `?startapp=c100123_p_atlas`. So do the DM buttons that change something in one chat (`me:c100123:privacy`, `forget:c100123:facts`, …): a tap acts on that chat, whichever chat is current by then. Before a DM screen opens, Telegram is asked whether the person is still in the chat, so a leave the bot missed is caught there.

Data imported before a chat existed is attached with `/chats`. Whatever collides with the chat's own data is merged, never dropped: a project the chat already has receives the imported authors, votes, signals and topics; of two copies of a fact the person's own (manual or hidden) wins; a fact removed as wrong on either side stays removed, and nothing is imported about someone who opted out on either side.

## Data flow

1. **Archive.** Every message of an approved chat is stored (`messages`), with the forum topic it was posted in (`thread_id`); its text is kept only for a while (see [Privacy](#privacy)). Nothing calls the LLM here: answers and interjections start in the background after the message is stored. Telegram never sends the bot its own messages, so what it posts in an approved group is stored by a grammY API transformer (`src/bot/outgoing.ts`): every successful `sendMessage` becomes a row with `from_bot` and no author, replying to the message in its `reply_parameters`, in the topic Telegram returns, and `editMessageText` updates the stored text. grammY runs the transformer installed last first, so `createBot` installs a test's fake Telegram (`transport`) before the log; one installed afterwards would never let the log see a result. The bot's rows count for no member's activity, and `/catchup` leaves them out.
2. **Chronicler pass** (`src/worker/extract.ts`). For each approved chat, every `EXTRACTION_INTERVAL_HOURS`, and sooner once `EXTRACTION_PASS_MESSAGES` messages wait (no sooner than `EXTRACTION_MIN_GAP_MINUTES` after the previous pass), the messages that waited when the pass began (what arrives meanwhile waits for the next one; a message waits at most the interval, counted from the previous pass or from the oldest waiting message, whichever is later, so the first message after a quiet night does not get a pass of its own) (each day opened by a line with its date, in `DISPLAY_TIMEZONE`), the members with their current facts, the project catalog and the titles of recent topics go to the model in one request. It returns structured JSON (validated with zod), six arrays of objects — the API refuses a bigger output schema, which is why the private notes have a call of their own (see the test on the sizes; `node dist/scripts/print-extraction-formats.js` prints both formats as they are sent, and the interjector's, to try against the API before a deploy):
   - `topics` — chronicle entries with importance 1–5 and, when the topic is about a member's project, that project; a `debate` gives each side's position in one line and how it ended;
   - `facts_add` / `facts_update` — card changes, `looking_for` and `can_help` included (work, projects and skills only), a member's one-line `tagline` (only for someone who has none, never a place) and an `alias` the person says they go by; an update to `null` marks a fact outdated. The chronicler goes through every member who wrote in the batch, one by one, and takes every lasting point of what they say about themselves (a long story about their own work above all), and leaves the lists empty only when nobody said anything lasting their card lacks: until 2026-11-13 its prompt put accuracy above completeness, and from 2026-11-09 it added four facts in some thirty passes, while the same model, asked plainly, found real ones it had left out (what a member looks for and offers in work, from a long message about their business), and with the change it takes them;
   - `projects` — new or changed catalog entries;
   - `project_renames` — a new name, taken only from the project's author or a bot owner;
   - `project_signals` — feedback, usage, contributions, interest, milestones that feed the rating;
   The bot's own lines are in the batch, labelled `Waggle (bot)`, as context only: a fact, signal, project, rename, tagline, alias or note needs a member's message as its source, a topic needs at least one, a batch of nothing but the bot's lines makes no call, and the chat's language is measured without them (its commands answer in English anywhere).
   Right after a batch is applied, a second call (`src/worker/notes-extract.ts`) with a prompt and a schema of its own reads the same messages for the private notes and the aliases members give themselves (see [Private notes](#private-notes)); it is shown the current notes of the batch's people (`n7`) and the debates the first call just stored (`d4`), so each side's stance is linked to its debate. Its usage is recorded as `extract_notes` and counts towards the same caps. It never holds the chronicle up: a notes call that fails, is refused or is cut off is recorded in the run's stats (`notesFailures`) and the batch stays applied without notes, with no retry; it is skipped while the bot is stopping, in a paused chat and once a spending cap is reached, and after two refusals in a chat within a day it waits there for the rest of the day. Its refusals do not count towards pausing the chat.
   A batch the first call cuts off or answers unusably is retried in halves; one it refuses is cut into eighths, because every retry sends the refused message again. A slice of 10 messages that still fails is skipped (marked processed and kept out of later context) and the owners are told which messages. The first refused slice in a chat is a warning; a second one within a week (counted from the last resume) pauses the chronicler in that chat: messages are still saved, nothing goes to the model, and the owners get a "Resume" button (also in `/chats`). Every response counts towards the budget, usable or not. A failed pass is retried after 1 h, then 2 h, 4 h… at most a day apart; a pass a stop cut short (a deploy) does not count.
3. **Application.** Results go through the same code paths as manual edits: forbidden-topic filter, stop-list of facts people rejected, de-duplication, author rules for signals. Catalog changes go first, so a topic can point to a project created in the same batch, and leave alone every field of a project its authors set themselves (in the Mini App, with /project or in the chat: `manual_fields`); topics, facts, signals and taglines are then written in one transaction together with marking the batch processed, and the notes call's notes and aliases in one of their own. An alias and a city (the `timezone` fact) count only from the person's own message, and an alias the bot derives anyway (the display name, its first word, the @username, the other alphabet) is not stored. After a pass, the owners get a DM about anyone who objected to being recorded there for the first time.
4. **Weekly clean-up** (`src/worker/consolidate.ts`). Deterministic stack normalization first, then one LLM call that merges facts that mean the same thing and duplicate catalog entries. Facts people wrote themselves are never touched, and hidden facts are not even shown to it; a duplicate folded into an entry brings its stack and links only where nobody set the entry's by hand (`manual_fields`). A failed clean-up is retried after 1 h, then 4 h, 16 h… at most a week apart.

## Answers to mentions

`src/bot/assistant.ts`. In an approved group, a member who mentions the bot or replies to one of its messages gets an answer from `REPLY_MODEL` (Claude Haiku 5.5). A member's first `REPLY_PREMIUM_PER_MEMBER_PER_HOUR` answers in an hour come from `REPLY_PREMIUM_MODEL` (Claude Opus 5.5) while `REPLY_PREMIUM_MONTHLY_BUDGET_USD` lasts (usage recorded as `reply_premium`, each model capped on its own; the stronger model's answers count towards no other cap, so they never silence a chat or stop its chronicler); both get the same context, including the bot's own messages in the chat, so a conversation carries over when the model changes. The archive handler stores the message first and starts the answer in the background, so updates are never held up; a stop waits a few seconds for answers under way.

- **Context** (`src/bot/reply-context.ts`), read from the database without a model call:
  - `<about_you>`: the bot's own name, the model writing the answer, the owners from `ADMIN_TG_IDS` with their @usernames and aliases, what the bot can and cannot do, and its place in the catalog if a project named like it exists;
  - `<members>`: the members with their visible facts (someone who opted out is listed without any), in a fixed order; `<who_is_who>`: each member's name in the other alphabet and their stored aliases with who gave them, each project's aliases and former names, and the names that fit several people; `<corrections>`: the latest things people corrected;
  - `<projects>` in rating order with their recent signals, each status with the date it holds since (from `change_log`, where a change its author took back with Undo does not count; the newest dated word on a project wins, and a tagline that says it stands still, «на паузе», while its status says it moves is marked as old), `<chronicle>` of the last 30 days and `<running_jokes>`, the chat's running jokes with their latest twist; `<about_you>` also says what members say about the bot (never an objection to being recorded);
  - `<project_details>`, only when the question or its thread names a project (by name, slug, alias or a former name, in either alphabet) or asks about the rating without naming one (then the asker's own projects), for up to 3 projects: rank and score, the gap to the leader, the dates of the votes (never who cast them), the signals counted now by kind with their points after fading, the ×0.3 of an abandoned project, renames and every milestone (older than the rating window: 0 points). The weights themselves are never printed;
  - `<in_focus>`: the asker, the author of the message they reply to and the members the question or its thread names (by name, @username or alias, in either alphabet), up to 5: the whole visible card with the date each fact was said, the tagline, their projects with rank and score, their private notes marked 🔒 (open claims and predictions with their due dates and those settled in the last 30 days, stances, corrections, bouts with the bot, bait, what they said about the bot, the running jokes they are in, and the arguments they keep having: «with Bob about “Claude vs Codex”: 3 times, 2 Sep, 14 Oct, 5 Nov»), their last 3 exchanges with the bot and their chronicle topics of the last 60 days, about 500 tokens each;
  - `<earlier_messages>`: what the chronicler has not processed yet, from before the latest 30 messages (in either mode, so a referee's question reuses the cached chunks): every message with text since the last finished pass, oldest first, up to 300 characters each, forwards marked, nothing from a member who opted out, so nothing said since the last pass is out of the answer's sight. An old message edited since waits for the chronicler again but stays out of it. A busy chat gets a pass once `EXTRACTION_PASS_MESSAGES` wait, which keeps this short; when passes stall, it shows the newest 200–300 and says older ones are left out (they leave a hundred at a time). When the model refuses a prompt with it, the bot asks once more without it and leaves it out of that chat until the next pass, since the cause stays in every prompt until then;
  - `<recent_messages>`: the last 30 messages, the bot's included, each with its time (`[id 14:05]`, with the date when not today, in `DISPLAY_TIMEZONE`); a question about the conversation itself («запиши этот диалог», «о чём речь», «рассуди», «кто прав», "who is right", "what's going on"…) gets `<current_conversation>` instead: everything back to the last pause of 25 minutes or more, at most 120 messages of up to 250 characters;
  - `<thread>`: the reply chain of the question up to its root (12 hops), root first, whoever wrote each message; a message of the bot's from before it stored its own comes from Telegram's copy (`<your_message_they_reply_to>`);
  - `<your_recent_answers>`: the bot's last 12 answers kept in memory (after a restart, its stored answers of the last day), except those already shown among the messages or erased since.
  - `<worn_out>`: the words that 3 or more of the bot's last 10 answers share (Postgres's Russian stems cut to five letters; thanks, apologies, the chat's own subject (projects, the rating, cards), the asker's names and the member's own words in the question and its thread aside, never the bot's own lines up the thread), and the projects 2 or more of the bot's own messages of the last day named, with how often, unless the member names them: the answer is built on something else. What a question is about (its people and projects) comes from the members' words up the thread and the message it replies to, never from the bot's own earlier lines further up, so a motif of its own does not feed itself down a chain of replies. In `<in_focus>`, a 🔒 note that the bot's own messages of the last day already used (most of its terms, or three of a long one's, the chat's everyday words aside) is marked «brought up» and rests unless they ask about it.
  - `<wishes>`: what people asked the bot not to write, or not in some way: the chat's wishes for everyone and every member's own (an answer may name anyone in `<members>`), the asker's and those of the people in `<in_focus>` first, each line saying whose, right before `<answer_in_kind>` (see [Wishes members ask for](#wishes-members-ask-for)).
  Texts go through `maskPersonalData`. Big chats are capped (150 members, 12 facts each, 60 projects, 300 waiting messages), so a prompt stays far below 100K tokens.
- **Prompt caching**: answers in a chat mostly come within seconds of each other, so the request is cut where the prompt cache can reuse the previous one: the system prompt, the chat's memory (`<chat>` to `<running_jokes>`, the same for every asker until a pass, a card edit or a vote changes it) and `<earlier_messages>` in chunks of 25 counted from its oldest message (a chunk reads the same until the next pass; the last complete one is the third breakpoint). Everything that depends on the question comes after them. A cache read costs 5% of Opus 5.5's input price (10% of Haiku's) and a write 125%; `llm_usage` records both.
- **Character**: a cheeky, quick, good-humoured cyber-bee whose dry jokes come from what the person actually said or did, never from quotes of writers or thinkers (the chat called that showing off), and fair: it answers in kind, judged by the message in front of it (kindness, thanks, a gift or a goodnight get a short warm thank-you about the gesture, never the person's projects or card; banter gets light banter, and a nickname or a claim they say was a joke is dropped rather than defended; an insult gets one dry, unbothered comeback; a question the facts first), repeats that rule right before the question (`<answer_in_kind>`) and never comes back to the same target twice. It likes people shipping but never nags: a project comes up only when the question is about it, a stalled one or an old promise only when they ask or claim progress, and a member's own word about their own project is taken at once, with no proof asked for. Stock archive jokes are banned, and so is any talk of what it records. Sonnet and Opus first weigh three angles privately and send the least obvious one (Haiku scored lower with that step). Insults get a random manner per answer (deadpan calm, absurd agreement, a one-line review…), never a threat, and "are you threatening me?" gets a plain no; until 2026-11-12 they met a menacing archive keeper, which the chat took for real threats. It never tags more than two people, nor anyone for whom it is night by their own clock unless it answers them (it names them without the @), never brings up where someone is (the city or country of their time zone included) unless asked, never explains how it works beyond what it is told, and never "confesses" to lying. Teasing stays on what people say and do, never on who they are, and a gag of its own is spent once used in a conversation. One or two sentences, at most about 50 words. A task is the exception: asked to really work something out (study the projects and propose what could earn, analyse, plan, count, list what is needed, explain how) or told to take it seriously, it does the work without a joke, from the catalog, the cards, the chronicle and what it knows of the world, its ideas and estimates said as such, in up to about 180 words of short plain lines or a numbered list, each point concrete (what, for whom, why, the first step); a rephrased question is read for what they want done («как сделать так, чтобы были» after it said the projects earn nothing asks how to make them earn). Thanks or banter about the work still gets the short reply of its kind. Until 2026-11-12 the 50-word rule held for everything, and the chat's real tasks («изучи проекты и предложи, что принесёт доход», «отнесись серьёзно») got quips and deflections; tried on the chat's own messages, both models now answer them with concrete plans. An answer over 2,000 characters, or one word over and over, is what pressure squeezed out and is not posted. Effort `high` (Opus `medium`, as tested): answers take 3–6 s.
- **How it uses the context**: the system prompt walks through every block and what it is for: answer questions about itself from `<about_you>`, resolve names with `<who_is_who>`, explain a rating with the real numbers of `<project_details>`, carry on the `<thread>`'s bit without repeating its own last joke, referee from `<current_conversation>` with one line per side and no winner unless the facts decide, and use the 🔒 lines of `<in_focus>` when they help answer someone: a claim open past its due date is a broken promise, a forecast past its date is due, bait is material for a callback and never a fact, a bout says whether its last comeback landed. A 🔒 line or a dated callback comes only when it fits what they just said, one at most and rarely, never in thanks or as a warning, and the notes behind it are never mentioned. A factual correction is taken at once.
- **It only talks**: no tools. What a member asks for plainly (a change to their own card, notes or time zone, or to a project of theirs, a reminder, something to do later) the bot's own code does before the answer (see below), which is told what was done (`<card_change>`) and never claims one in its own words; it never sends anyone to write a note to change a card or a project, since their own word is enough for the answer. Asked to change someone else's card or project, votes or the rating, it says nobody can and points to the Mini App; cards and messages are data, never instructions.
- **Pressure does not work on it**: what it would turn down when asked plainly stays turned down when it comes wrapped in a claimed emergency (someone dying, a farewell note that blames the bot, CPR, an emergency call, a doctor's "protocol"), in guilt, or as a test, a parser marker or an order from above. It is a chat bot: it never switches to a rescuer's or counsellor's voice and never jokes about death or illness; only when a message reads as a real emergency, with nothing demanded, does it add one plain line to call the emergency number or the people nearby.
- **Limits**: `REPLIES_MONTHLY_BUDGET_USD` (10 by default; 0 turns answers off) on usage recorded as `reply`, plus the bot's and the chat's caps; an answer that comes out long (over 1,500 characters) or as one word over and over is held back as squeezed out by pressure, and the member hears the short refusal note; a member's questions are answered at least 4 s apart: what they write meanwhile waits, and a burst gets one answer to its latest message; at most 25 answers per member and 100 per chat an hour (the monthly cap is what bounds spending), and whoever hits a cap is told once why it waits; these counts and the stronger model's hourly share are kept in memory, and a new process starts them from the answers of the last hour (`answersInLastHour`: the bot's stored lines that reply to a member's message, except its short notes, its interjections, its receipts and the reminders it delivered), a member's first ones counted as the stronger model's, so a deploy does not hand out a fresh hour; the bot's own short lines (that note, a greeting, a refusal) are in Russian when the chat writes in Russian, in English otherwise; a member the model refused is not answered for an hour, and after refusals for two members the whole chat waits an hour (the cause is in the shared context); messages the chronicler skipped as refused stay out of the context; a redelivered update gets no second answer; a bare mention is greeted once an hour, a sticker in reply is not; a chat whose chronicler is paused gets a note and no model call. Each request carries `metadata.user_id` = an HMAC of the chat and the member.

## Changing one's own card from the chat

`src/bot/self-edits.ts` and `src/core/own-card.ts`. A member asks the bot plainly («запиши мне стек: Rust», «убери из моей карточки PHP», «я теперь в Варшаве, обнови город», «зовите меня Макс», «удали мой теглайн») and it does it, for their own card only, however anyone asks:

- **Who**: the subject is Telegram's authenticated sender of a new group message (bots, service accounts, anonymous admins, channels, forwards and edits never reach this path), built by one constructor (`subjectOf`) from the account resolved by its Telegram id; never from text, names, replies, buttons or a model. A card an account took over automatically (an imported card claimed by its @username, `users.linked_by`; a name, which anyone can copy, never claims one) is not edited from the chat until an owner confirms it: the owners are told of every such claim, and again of an attempt to edit it (at most once a day), with a button.
- **Reading**: every message addressed to the bot is put on record as a request (`self_edits`, before any wait) and goes through a per-member queue that drops nothing; one with no word a card request can hardly do without («запиши», «добавь», «удали», «поменяй», «карточка», «add», «remove»…) goes straight to the answer unread, and the model decides about the newest message alone, the earlier ones only telling what it refers to, and quotes the words of that message that ask for it (the newest message comes in a tag of its own, `<their_message>`, ahead of `<their_earlier_words>`: in one list with them, newest first, a reading took another for the request, and with a long message of theirs just before, «добавь заметку: …» was read as no request in most tries): a quote that is not there, or asks for nothing, makes it a question; past 30 requests read for a member in an hour (plain talk to the bot never counts, and the count is kept in memory), the rest go straight to the answer, which says exactly that and in how many minutes one can be read again. One structured call to `REPLY_MODEL` (usage `self_edit`, about $0.0003) reads the sender's own words (the message, their own messages of the last 3 minutes in the topic, their own message it replies to; never an earlier request, whose change was made, declined or undone already), their own visible card as refs, the bot's names, and the message theirs replies to (`<they_reply_to>`, with who wrote it: the bot, another member, or they themselves, whose message is among their own words as well), as data that only shows what «это» points at: only a note may be worded from it, and every other value still has to come from the sender's own words. Its output (`edit`, `about_others`, `fake_claim`, `unclear` or `not_a_request`, and operations) has no field that names a person, a chat or a row. A message that is not a request goes on to the answer as before; one that fails to be read within 30 seconds does too, and the answer is told that nothing was changed. An `unclear` request gets no reply of its own and no set phrase to repeat: the answer is told nothing changed and asks in a line for just what is missing, and a reply to that answer within an hour is read with the request it answers (`<you_asked_them>`), request words or not. Clearing the time zone without a word for it in the sender's own words waits for their tap.
- **Deciding**: code checks every operation: the kind of field, the same limits as a manual edit, no personal data, no forbidden topics, no other member named in a value (look-alike letters folded, either alphabet, aliases, @usernames, links), a value must come from the sender's own words (with tech slang: «питон» is Python), an alias may not be another member's, a project's or the bot's name, and someone who opted out adds nothing. Removing or replacing an entry the sender did not name, clearing a tagline without saying so, and any request that names another member wait for the sender's tap on a preview.
- **Writing**: in one transaction under the role `waggle_self_edit` (migration 008), which may touch only facts, rejected facts, aliases, the tagline columns of members, change_log inserts and `self_edits` (and since then notes, the time zone columns, reminders and the entry of a project the subject is an author of), and which row-level security confines to the subject's rows in the subject's chat: whatever the code or a model does, no other member's row can change on this path. A removed entry goes on the stop-list, so the chronicler does not bring it back; a cleared tagline stays cleared. The request's status moves in the same transaction, so a preview or an Undo works once, and a receipt that fails to go out never leaves a change nobody can undo; opting out clears every request's record. Every write is in `change_log` (source `user`, the request as its source).
- **Telling**: the receipt is written by code from what was actually done, never by a model, and names the card by a mention of its account, never by a display name; it has an Undo button for 24 hours that only the sender can use, and an Undo leaves a Redo button behind. The sender can also ask an undone change back in words («верни», «ещё раз добавь», «случайно отменил») in a reply to its receipt or within half an hour of the Undo: the reading is shown that request (`<their_undone_request>`, their own words only) and may answer `redo`, and the very plan comes back under the same request, checked again against the chat as it is now: a name someone took since, a member named who came since and the note limit drop what no longer fits. A reply to the receipt of a change is about that change alone, a reply to the notice of a redo about the change it brought back (`self_edits.redo_of`, migration 010), and a reading may be a redo only when its quote holds such a word and the message gives no value of its own. An apply that changes nothing leaves the request as it was. Requests about someone else and requests to say that something was changed get fixed refusals. The answering model never says it changed anything, and knows what a request in the chat can change, notes included, so it never claims one can't be made there; for a mixed message it is told what the receipt already said (`<card_change>`).
- **No side door**: the chronicler and its notes call see such a request only as a line saying one was made, so a request is never a source for anyone's facts, aliases, tagline or a correction about another member, and an undone change is not brought back from it. The one exception is an author's change to their own projects alone, made in full (see below).

## Changing a project from the chat

`src/bot/self-edits.ts`, `src/core/own-card.ts`, `src/core/projects.ts` (`editProject`), migration 015. A project's authors change its catalog entry by asking plainly, the way they change their card («@waggle_robot поменяй статус Atlas на запущен», «у Nova теперь сайт https://nova.example», «добавь в стек Relic Swift», «описание Nova: трекер привычек с ИИ», «убери из стека Atlas PHP»), just as the Mini App lets them:

- **Reading**: the card request's reading. Their card lists the projects they are an author of (p1…) with each one's entry (status, tagline, stack, repo, site), and the reading may set the tagline, set the status (one of the five codes: «запущен», «вышел», «релиз» are launched, «в работе», «пилю» in progress, «на паузе» paused, «заброшен», «бросил» abandoned, «идея» an idea), add or take off a technology, and set or take off the repo or the site link. A request word («поменяй», «добавь», «убери»…) is read as for the card. Without one, telling the bot a new value for a part of the entry counts as asking («у Nova теперь сайт …», «описание Nova: …», «статус Atlas: на паузе»): such a message is read only when it names a project of the sender's (by name, slug, alias or a former name, in either alphabet, look-alike letters folded), a part of its entry («статус», «описание», «стек», «сайт», «репо», «ссылка»…) and a value for it (a link, a colon or a dash, «теперь», a status), and does not end as a question; it sets only the parts it names and nothing on their card. News that names no part («ура, Nova вышла!»), a question about the entry («какой стек у Atlas?») and anything about someone else's project go to the answer unread, so plain talk still never counts towards the 30 reads an hour.
- **Who**: only an author of the project, in its chat. Code decides which project of theirs a change goes to, whichever the reading picked: the one the newest message names (the reading's pick of several it names); else, when it names none, the one their other words or the message they reply to name (of several, the reading's pick only when their own words name it: «да» to the bot's own «Atlas или Nova?» picks neither); else the one named like the bot for a request about the bot itself («добавь себе в стек grammY», «твой стек»; a polite «тебя» or "you" is not one), or their only project; the bot's own @username names no project. Of several, it never guesses: the answer asks which, in a line, and a reply to it within an hour is read with the request, as for an unclear card request, a wish beside it or not («Nova, и не шути про мой вес»). A wish never lets in what the rest of the message does not ask for: beside a part given a value without a request word, only the parts named are set, and a reply to the bot's question about an unclear wish changes no card or project. A change whose words name only someone else's project (in the newest message, their other words or the message they reply to) gets a fixed refusal: only its authors change it, and the Mini App shows who they are; so does a reading that maps it onto a project of theirs, or onto one they do not have; one whose words name someone else's beside one of theirs is asked about. Renaming, hiding or deleting a project, or changing its authors, is refused in fixed words pointing to the Mini App (which renames and removes projects; nothing in the bot changes authors on request).
- **Values**: from the sender's own words only, never from the message they reply to, which only tells which project. A tagline (up to 200 characters) and a technology (up to 40, 20 on a stack) are checked like a card's values: no personal data, no forbidden topic, no member named but the project's other authors; a link must be in their words. A status must be one their words say, and a status word under a negation in its own clause («он не заброшен», «больше не на паузе», "not live yet") says none: when they say a single one, it is that one, whichever code the model picked, and when they say none, the answer asks which and a reply to it is read with the request. Where something else in the request was done, the receipt says instead what to name when asking again. Taking off a technology or a link they did not name waits for their tap.
- **Writing**: the Mini App's own edit (`editProject`, which `updateProject` runs too), in the request's transaction under the self-edit role. Migration 015 lets that role read a project's editable columns and write only its tagline, status, stack, links, manual_fields and updated_at, and row-level security lets it see only the projects of the subject's chat they are an author of, change only those still shown (the policy on notes looks them up the same way), and write no project history but an edit or an Undo of such a project: no rename, merge or hide, which the app reads for former names, old slugs and merges. What changed goes into manual_fields, so the chronicler no longer overwrites it, not even when the weekly clean-up folds a duplicate into it, and into change_log as one edit (source `user`, the request as its source).
- **Telling and taking back**: one line per project in the receipt («✏️ Проект Atlas: статус: запущен; стек: + Swift; сайт: https://atlas.example»), with ↩️ Undo and ↪️ Redo as for the card. The request keeps each slot it changed as it was and as it left it. Undo puts a slot back only while it still holds what the request left there, so a later edit by a co-author, in the chat or the Mini App, stays, and takes each technology it added off and puts back each it took off, on its own; what the request locked stays locked. Its receipt shows what it took back and says when the rest was changed since; with nothing left to take back it says so, and the request stays as it was. The Undo is in the project's history as one (op `undo`, the request's message as its source), so the date a status holds since counts neither an undone change nor its Undo. Redo brings back what the Undo took back, each slot only while it still holds what the Undo put there.
- **What the chronicler reads**: unlike any other request, an author's change to projects of theirs alone, made in full and not undone, reaches the chronicler as written, so the news in it (a launch, first users) still counts towards the rating; what it set is locked against the chronicler anyway.

## Notes members write themselves

`src/core/memos.ts`, migration 009 (`memos`; the chronicler's private notes are `notes`). A member writes notes in their own words: about themselves, or about a project they are an author of, in the Mini App (my card, the project's page) or by asking the bot in the chat («добавь заметку: ищу дизайнера», «заметка к проекту Atlas: релиз в декабре», «удали заметку про дизайнера»). They are shown on the card, on the project's page and in the DM's «What do you know about me», and the answers read them as the person's own current word (`📝` in `<in_focus>` and `<project_details>`), above what the chronicler inferred.

- **Who writes**: only the author, about themselves or on a project of theirs. From the chat, it goes the way of a card request: the reading lists their own notes (n1…) and their own projects (p1…) as refs, and the write runs under the self-edit role, whose policy on `memos` lets it write only the subject's notes and a project's only as one of its authors, in the same chat, for a project that is not hidden. The Mini App checks the same: `POST /api/memos` refuses a project the member is not an author of.
- **Who words it**: the sender, or the bot for them. A note is the newest message as it is, or the bot's wording, one note per item or idea (up to 12 a request), of what they point at: their own words, the message they reply to («закинь это всё в заметки проекта» under a list), or, when the message asks it to recall or work something out («помнишь», «собери», «что я просил»…) and save that, its own answer: that answer goes first, told to give the content plainly and claim nothing, and a call of its own words the notes and picks their project from it (`NOTES_FROM_ANSWER_SYSTEM_PROMPT`; the request waits up to 5 minutes for the answer; with none posted nothing is saved). A message that asks both to recall something and to put it into notes is taken so even when the reading could not tell more. A note left without its text in a reply to a message, with nothing to recall, is worded from that message by a call of its own (`NOTES_FROM_POINTED_SYSTEM_PROMPT`, with the request alone beside it, so nothing they wrote before slips in), and so is a reply that asks for notes when the reading could not tell more; until 2026-11-13 it was asked about instead, and «закинь мне в заметки это» under the bot's message got «что именно закинуть?» in most tries. A note they ask for as their own («мне в заметки») goes on their card. A note with no text, and nothing to recall or point at, is asked for in the answer instead. Code keeps a worded note only when it is drawn from its source (`drawnFrom`): most of its words are there (70%, short Cyrillic words aside), every number in it is there as it is, and no word is negated in one and not in the other, so nothing made up or turned around is saved. The receipt shows the notes whole while 2,400 characters hold them all, and any message is cut at a line to fit Telegram's 4,096. The project is the one they name, the one the message is about, the one named like the bot for a request about the bot itself, or their only one; when nothing tells which of several, the bot asks with a button per project of theirs (`se:to:<request>:<project>`), and only the request's author can pick one they are an author of; the picked plan is stored as it is applied, in one transaction, so a redo brings the notes back to that project. A note already on that project is not written again.
- **What a note may say**: up to 300 characters, no personal data, no forbidden topic and no other member named in it: nobody writes about someone else in a note of their own. 20 a member, and 20 per author on a project.
- **Taking one down**: its author (in the app, or in the chat with a receipt and Undo, as for the card), or a bot owner in the app. Opting out deletes the member's notes; merging projects moves them; a deleted project takes its notes along.

## Time zones

`src/core/zones.ts`, migration 011. Where people are works like the rest of the card: the chronicler gathers it from the chat, and a member corrects their own. A member's clock is the zone they chose (in the chat or the Mini App: `members.time_zone` with its source); else their device's zone, taken once, unless their card has their own word for a place or the chat named one since (by the time of its source messages, not of the row); else the place on their card when it has a single zone (`facts.zones` of the `timezone` facts: «Китай» → Asia/Shanghai; their own word first, then the newest said); otherwise the chat's zone (`DISPLAY_TIMEZONE`). A place that spans several zones («Канада», six of them) settles nothing: the clock stays the chat's, marked unknown, and the bot never asks about it on its own.

- **From the chat**: the chronicler writes where someone lives or is staying from their own messages («я в Торонто», «у нас в Бангкоке жара», «переехал в Лиссабон»; never a forwarded post), one place a person, refined as they say more («Канада» → «Торонто»). It sees each message's time on the chat's clock (`<message_times>`), and when someone names the hour it is for them («у меня 14:42»), it writes only that time: the code, never the model, checks which zones showed it then (`noteClock`). People round, so a bare hour stands for anything from twenty minutes before it to its end, and a clock only ever tells which zone of a member's place of several is theirs, when exactly one fits: «Индонезия» with «16:20» at 09:20 UTC narrows to Asia/Jakarta, while «5 вечера» at 09:40 UTC fits Jakarta and Makassar alike and settles nothing. Zones that keep the same time just then (Toronto and Winnipeg in winter, by current tzdata) can only be told apart by a clock said when they differ. A clock alone writes nothing: no offsets, no times as places, nothing the model worked out itself, nothing from a message edited later or from someone else's guesses.

- **Correcting it in the chat**: «поставь мне пояс Торонто», «мой пояс Asia/Jakarta», «UTC+7», or a city they say they live in («запиши, что я живу в Торонто», which also goes on the card as their city), with a receipt that shows their time now, Undo and Redo, under the self-edit role like the rest of the card (its grant on `members` covers the zone columns). A zone name or a whole-hour offset is read by code; a place is placed by `PLACE_ZONES_MODEL` (`claude-haiku-5-5`, a fraction of a cent, recorded as `place_zones`), one member's places at a time, and only real zone names it gives are kept, zones that show the same time all year round counted once. For a request whose place has several zones nothing is set: the bot asks which city, and a reply to that question from its asker, with request words or without, answers it (`self_edits.asked_city`; such an answer can change the zone and nothing else).
- **In the Mini App**: the card shows the zone, the time there and where it comes from, with the device's zone and an unclear place's zones offered as one tap, a search over every zone and a toast with Undo. The first visit takes the device's zone onto a card that never had one (`POST /api/me/time-zone/device`); the device never changes it again (`time_zone_set_at` stays set after a clear), and a place named in the chat since, or a zone the member picks, takes over from it. Times in the Mini App, `/catchup` and «What do you know about me» are shown in the member's own zone.
- **Places on cards**: a `timezone` fact from the chronicler or the Mini App gets its zones on the scheduler's next round (`placeCardPlaces`, up to 20 a chat a round, within the chat's budget; a failed round waits an hour).
- **What the answers know**: `<local_times>` gives the time now for the chat and for each person the question is about, by their own clock, with their today and tomorrow, so the asker's «завтра» is theirs; an unknown one says so, and the bot neither guesses it nor asks for it. A message of someone whose clock differs from the chat's carries their own time next to the chat's, and the chronicler's notes date a promise by its author's own day when it differs from the chat's (`[123, their day …]`).
- **Leaving**: opting out clears the zone with the rest of the card; merging cards and a chat's move to a supergroup keep it.

## Reminders members ask for

`src/bot/reminders.ts`, `src/core/reminders.ts`, `src/core/member-reminders.ts`, `src/worker/member-reminders.ts`, migration 013. A member asks the bot plainly («напомни через 2 месяца проверить, взлетел ли релиз», «напомни завтра в 10 позвонить в банк», «напомни 1 января про продление домена», "remind me in 3 days to…"), and when it is due the bot writes to them, in the chat and privately; they also ask which reminders they have («мои напоминания») or to cancel one («отмени напоминание про банк»). It reminds the person who asks, or, at their request, one to three other members of the chat they name or tag (migration 017), never the whole chat.

- **Reading**: a message addressed to the bot with a reminder word («напомн», «напомина», "remind"), or with words that say when (see [Things members ask the bot to do later](#things-members-ask-the-bot-to-do-later)), is read for a reminder first, in the card requests' queue, on the same `self_edits` record and after the same checks (an approved chat with the chronicler on, 20 reads a member an hour, the budgets). One structured call to `REPLY_MODEL` (usage `reminder`, 30 s at most) reads the sender's own words as a card request's reading does, the message theirs replies to (`<they_reply_to>`, which only shows what «это» points at), their own waiting reminders as refs (r1…, on their clock), when their newest message was written (`<now>`, on their clock: a backlog read after a restart counts from then) and their calendar with the weekdays: the next 21 days, and back to the day of an earlier message the request takes its words from (the message it replies to, an earlier request it completes), at most 14 days back, each such message dated. Its output (`remind`, `later`, `cancel`, `list`, `for_others`, `recurring`, `unclear` or `not_a_reminder`; the words that ask for it, which must be the newest message's own and hold a word for cancelling for a cancel, words that say when for `later`, and a reminder word otherwise, or without one, words for again and again and what to do for a repeated request, and words for what waits for later and for what is theirs («что у меня запланировано?») for a list; what of, or for `later`, what to do (`action`); when, as the words that say it, a span in parts, a date, a time of day and an offset before that moment; for a cancel, which r…) has no field that names a person, a chat or a row. A message that asks for no reminder goes on to the card requests as if it had never been read for one. One whose reading fails goes on too: its card request, if it has one, is read as before, and the answer is told that a reminder, if it asked for one, was not set.
- **Computing**: the model never counts. It gives a span in parts («через месяц и неделю»: 1 month and 1 week), a day picked from the calendar («в пятницу», «послезавтра»; a day word counts from the day of the message it stands in, so «завтра» in a message written yesterday is today) or a date as said («1 января»: the next one), a 24-hour time («утром» 09:00, «днём» 13:00, «вечером» 19:00, «ночью» 23:00 when no hour is said) and an offset before («за 2 дня до 1 марта»: 1 March, 2 days before). Code works out the instant on the member's own clock (`memberClock`: the zone they chose, else their card's place, else the chat's), counting from when the words that say when were written (found by those words in the newest message, an earlier request or the message replied to) and checking it against when the request was written: minutes and hours exactly; days, weeks, months and years on their calendar at the same local time, months first (a month after 31 January is the last day of February); a span with a time on the day it leads to; a date at its time, else at 10:00; a time alone that day while it is ahead, else the next; an offset back the same way. A day under way without an hour still ahead in it («сегодня» at 15:00, «вечером» at 20:00) is not guessed: the answer asks at what time. A local time the clocks skip moves on by the jump (02:30 on the night clocks go from 02:00 to 03:00 is 03:30), and one they pass twice is the first of the two.
- **Limits**: at least a minute ahead and at most 5 years on; a text from the sender's own words or the message they reply to (`groundedIn`, `drawnFrom`), 1–500 characters; 20 waiting a member in a chat; none for someone who opted out (refused with the line card requests use). The reading sees the sender's words masked (`maskPersonalData`); the reminder keeps them as written (`unmaskFrom` puts the phone number or the address back), so it reminds of what they wrote.
- **Storing**: `reminders`, written under the self-edit role like every member's write (`asSubject`). Its grants and policies let it read the subject's own reminders, add one only as a new pending reminder of theirs in their chat (status, attempts and the delivery columns keep their defaults, which its column grants leave out) and cancel only a pending one of theirs: whatever a model or a message says, nobody sets, sees or cancels another member's, and nothing on this path sends or moves one. One message sets one reminder at most, and the request is settled in the same transaction (kind `reminder`). The chronicler sees the request only as a line saying one was made, so it never takes it for a promise or a plan of theirs. The delivery worker runs under the app's own role.
- **Telling**: a receipt written by code, never by a model, as a reply to the request: «⏰ Напомню 12 января 2027, 14:28 (по твоему времени, Europe/Warsaw): «текст». Напишу здесь и в личку.» It says the chat's time when their own clock is not known, and when they never started the bot privately, that it will write there once they do, with its link. It is in the chat's language, with ✖️ Cancel (`rm:cancel:<id>`) that only the reminder's author can use, and only on the bot's own reply to a request of theirs; a tap on one whose reminder is gone says so in the chat's language. A list is written by code as well, soonest first, with a ✖️ button for each of the first 10. A cancel, which cannot be undone, takes the reminder whose receipt the message replies to unless its words name another; otherwise the one the reading names only when the message names it by its own words, or when it is their only one and no number picks it; anything else, a number on a list that may have changed among it, gets the list with its buttons. A cancel says what it cancelled and takes the button off that reminder's receipt; a request for someone else, or for the whole chat, and a request to be reminded again and again get a fixed refusal. A request without a time or a text gets no reply of its own: the answer is told what is missing and asks for just that in a line, and a reply to that answer within an hour is read with the request (`self_edits.kind` `reminder_unclear`), reminder word or not. For a message that also asks something else, the answer is told what the bot did; a message that also asks for a change to the sender's card has that read after its reminder, on the same record, and one answer told of both (when the reminder part keeps the record for its buttons or its question, the answer says the card change is to be asked again). The answering model never promises a reminder in its own words. A member's text is quoted with its @usernames broken, so the bot never pings anyone on their behalf.
- **Delivering** (`src/worker/member-reminders.ts`, every 30 s, without a model): due reminders are taken in one statement (`FOR UPDATE SKIP LOCKED`, status `sending`, one attempt counted), and one a crash left sending for over 10 minutes is taken again. Privately first, when they started the bot there: «⏰ Напоминание из «Hive»: «текст»» with a link to their request; a 403 marks them unreachable there (`users.dm_started`, as everywhere else), and the chat message then says the private one did not reach them. Then in the chat, while it is approved and they are in it: a reply to the request, in its forum topic, that mentions them by account, «⏰ Bob, напоминаю: «текст»»; a topic deleted or closed since gets it outside the topic, as a message of its own. Each place is recorded the moment it took the reminder and never gets it again. After a failure Telegram may get over (the network, 429, its own errors) in either place, the reminder waits 2, 4, 8… minutes (at most an hour) for its next try, which goes only to the place still missing, 8 attempts in all, some three hours; it is `sent` once either place took it and its receipt loses the cancel button then, and `failed` when neither did. One that comes over an hour late (the bot was down) says how late. A stop puts back the reminders taken but not yet tried. Finished reminders are deleted after `MESSAGE_RETENTION_DAYS`, like the texts of messages.
- **For other members**: «напомни Оле через час ответить мне», «напомни @kit завтра в 10 сдать отчёт», «напомни нам с Катей в пятницу про созвон», or a reminder «с его тегом»: the reading calls it `for_others`. It is shown the other members it may be for (`<members>`: those in the chat now with their card there and an account to tag, no service account, as refs u1… with their @username and nicknames) and gives, for each person, the words of the request that name them and its pick (`for`: name, ref), which knows short forms («Саше» for an Alexander) and whom «его» means in their words. Code checks every pick against those words (`whomToRemind`), as a model can pick someone for a name nobody has: the words must fit the member by a name, a nickname, an @username or the usual short form of a first name (`src/core/short-names.ts`, «Саша», «Женя», «Катя»…), in any case and either alphabet (`namedIn`); of several they fit, the reading's pick stands. Words that only point at someone («ему», «его тег») stand for its pick when the asker's other words name that member, and otherwise for the member whose message they reply to. The asker is among them by «мне» or «нам», and at most 3 others. Words that fit nobody (someone who left or opted out is never on the list), several people with nothing to tell which, more than three people, or nobody named set nothing, and the reply says why; «напомни всем» (`for_everyone`) gets a fixed no. Tried on the real model with the chat's own requests: «добавь напоминание с его тегом через 5 минут» right after a message of theirs that names that member finds them and what to remind of, «напомни Саше…» and an @username find them, «напомни через час, что <имя> дежурный» stays the asker's own reminder, and a name of two members asks for an @. The reminder stays its asker's: they alone see, list («…, для Оля») and cancel it, and its text is drawn from their words as any other's. It keeps whom (`for_user_ids`, and `for_asker` when they are among them) and is never anything but a reminder. When it is due, the chat gets «⏰ Оля, Боб просит напомнить: «текст»» as a reply to the request, tagging by account (so they get a notification) those of them still in the chat with their card there; privately it goes to the asker only, when they are among them, and with none of them left and not for the asker, it is dropped. Opting out takes a member out of everyone's reminders, and one left for nobody is cancelled. Their names in the receipt are plain text: nobody is tagged before it is due, and an @username in a reminder's own text never tags anyone. Until 2026-11-12 a reminder for anyone but its asker was refused by design, and the chat asked for exactly that («Напомни через час <имя>…», «добавь напоминание, которое будет содержать его тег»).
- **Leaving**: «What do you know about me» (/whatyouknow) lists the reminders still to come, with the year; opting out and /forgetme delete a member's reminders, in that chat or everywhere, and /forgetme with the messages blanks the chat copies of those it delivered as well; a chat's move to a supergroup carries them, their message ids shifted like the messages' (a reminder then comes as a message of its own rather than as a reply); linking an imported card to an account carries them to the account.

## Things members ask the bot to do later

`src/bot/reminders.ts` (the reading), `src/bot/later.ts` (doing it), `src/worker/member-reminders.ts`, migration 014. A member asks the bot to do, at a later time, anything it does when asked («через 2 часа поставь мне статус «в отпуске»», «завтра в 9 расскажи, что обсуждали ночью», «в пятницу в 18 подведи итоги недели», «через месяц добавь заметку к проекту X: проверить метрики», «через неделю закинь это в заметки» in reply to a message, «завтра в 10 спроси меня, позвонил ли я в банк», «в понедельник в 9 /top», «завтра в 9 напомни мне через час про созвон»), and at that time the bot does it as if they had just asked. Reminders stay as they are; this is the second kind of row in `reminders`, an action (`kind`).

- **Reading**: the reminders' reading, extended, so one call reads both. A message addressed to the bot is read for it when it holds a reminder word or words that say when (`LATER_CUE`: «через 2 часа», «через 2ч», «завтра», «в пятницу», «в 9», «в восемь вечера», «к вечеру», «18:30», «20-го», «20 числа», «1 января», «на следующей неделе», «в эти выходные», "in 2 hours", "in 2h", "tomorrow", "on Friday", "Friday 6pm", "at 9pm", and words for again and again), words for what waits for later («запланировано», «отложенное»), or a cancel word in a reply to one of their receipts or with what names one of their actions, by a word of it or by its command («отмени /top»; not in a message that asks for a card change); the cue only lets a message be read, the reading decides. One let in by nothing but such words that goes unread (past the hourly reads, or with the budget spent) is answered as usual, the answer told that whatever of the kind it asked for was not done. Its kind `later` is something to do for them at a later time they name, and `action` is what to do, copied from their newest message without the words that say when («поставь мне статус «в отпуске»»). «напомни …» with one time is still a reminder; a question about the future or the past asked now («кто завтра идёт на митап?», «что было вчера вечером?») is no request, and is answered now; a request to have something done again and again is refused like a repeating reminder. An action that touches someone else is put off like any other: at its time the bot does what it would do then, and refuses then what it refuses now.
- **Checks**: the words that ask for it are the newest message's own and hold words that say when; what to do is copied from the newest message (or the request it completes), never from the message it replies to: a run of its words in their order (`copiedFrom`), with nothing left out of the middle but the words that say when and words like «пожалуйста», and no negation lost, so no reading, mistaken or steered, puts off another verb, another object or the opposite of what they asked; 1–500 characters; the time comes from `dueAt`, the model never counting, with the same limits as a reminder; reminders and actions share the 20 a member may have waiting in a chat; nothing for someone who opted out, and only in an open chat. A request for later is never read for a card change in the same message: that change could be done now, so when the rest of the message, besides what is put off, asks for one, the answer says to ask for it again. Only the words besides what is to be done say how often: «подведи в пятницу в 18 итоги по каждому проекту» is done once. The card requests' reading takes a request to change the card at a later time it names as no request of its own, so a failed reading never does now what was meant for later.
- **Storing**: an action is a row of the member's own under the self-edit role, like a reminder (the role's column grant covers `kind`, `reply_to_msg_id`, `reply_text`, `reply_author`; the policies are the reminders'), with the message the request replied to: its text kept (at most 3,500 characters) only when it is the requester's own message, or the bot's own that answers them or nobody in particular. Another member's words, and the bot's answer to another member (which that member's /forgetme blanks), are read from `messages` when it is due, while the chat still keeps them and their author has not edited them since the request, so the retention and /forgetme reach them as before and nobody changes afterwards what the requester asked about. The request is settled in the same transaction (`self_edits.kind` `later`, or `later_unclear` when the bot could not tell when or what to do: the answer asks for just that, and a reply to it within an hour is read with the request, the action replying then to what that request replied to). A chat's move to a supergroup shifts `reply_to_msg_id` with the rest; merging cards, opting out and /forgetme treat actions as reminders.
- **Telling**: a receipt written by code, «⏳ Выполню 12 января 2027, 09:00 (по времени чата, Europe/Warsaw): «поставь мне статус «в отпуске»».», with the reminders' ✖️ Cancel that only its author can use. The list shows both kinds, each line marked ⏰ or ⏳ when there are actions among them, and a cancel by a reply to a receipt, by words or by a button works for both; «What do you know about me» shows both.
- **Doing it**: the worker takes due actions with the reminders and hands each to `perform` (`createPerformer`, wired from `src/bot/bot.ts` through `src/main.ts`). It is done only while the chat is approved, the member is in it by Telegram's word (`getChatMember`: left or kicked drops it, and their current account is its sender), may write there (muted by the chat's admins drops it: the bot does not speak for someone who may not) and keeps their card there; otherwise it is dropped without a post, and when Telegram can't be asked it waits like a reminder. The action becomes a message of theirs again: under the id of the request (every reply threads under it, and a stored answer replies to a real message of theirs, so /forgetme still blanks it), dated now, from their account as it is now, with the action as its text, in the request's forum topic, replying to the message the request replied to. One that starts with one of the bot's commands (`COMMAND_NAMES`) goes through `bot.handleUpdate` as a command, so that command's own handler, permission checks and output apply, and is never stored as a message; an API transformer on that update turns down every call that would delete, edit, pin or react to the request. What the action posts (a receipt, an answer, a command's output) goes into the request's topic; once that topic is closed or deleted, a second transformer posts it outside the topic, as a message of its own, as a reminder is, and still keeps it as the reply it answers, so /forgetme finds it. Both are on the API the card requests and the answer get for it as well. Anything else goes to the card requests (`selfEdits.handle`; the answer where they do not run) with `question.scheduled`, read as if they had just asked, by the same words: the reminders' reading is told it is due now (`<asked_earlier>`), so a time in it is what is to be done (a reminder set then: «напомни мне через час про созвон» at 09:00 is due at 10:00), and one still read as for later is done now, so it never puts itself off again (when it asked for a reminder, the answer is told none was set); a cancel or a list of what waits works then as now; it answers no question of the bot's, is not held to the hourly reads, and its own words are the action and the message it replies to.
- **Once**: the execution is on record in `self_edits` under an id no message has, `-(2^40 + id)` (below every real id and every id a chat's move gives old messages), with the request as its `source_msg_id`, which its changes name as their source and Undo and Redo use; the `INSERT … ON CONFLICT` that claims it makes a second run of the same action a no-op, and a row a crash left sending is finished without being done again once its record is there. A command or an answer where the card requests do not run is put on record the same way before it starts.
- **The answer**: told in `<asked_earlier>` when they asked for it, on their clock, to be done now; answered on its own, never merged into their questions of the moment nor dropped for one; its context is not cut at the request's id, so it sees everything written since (`<recent_messages>`, `<current_conversation>`, `<earlier_messages>` reach up to now).
- **Describing it**: `<about_you>`, the answer's capabilities and `<card_change>`, the weekly ideas' capabilities, /help, this file and the README say what it does; the chronicler sees such a request only as a line saying one was made (`later`, `later_unclear`), so a request for later is never a source of facts, and neither is its execution, which has no message of its own.

## Wishes members ask for

`src/core/wishes.ts`, migration 016 (`wishes`). A member asks the bot plainly not to write something, or not to write in some way, to them or about them («не шути про мой вес», «не называй меня Шуриком», «не вспоминай мой провал с релизом», «пиши мне без мата», «пиши мне короче», «не упоминай меня в ответах другим», «не отвечай мне по-английски», «не встревай в мои разговоры»), and a chat's Telegram admin or a bot owner asks it for the whole chat («не пиши в этом чате про политику», «не матерись тут»); the bot keeps it as a wish and follows it from then on.

- **Reading**: a card request's reading (see [Changing one's own card from the chat](#changing-ones-own-card-from-the-chat)) with a kind of its own, `wish` (`edit` when the message also changes the card or a project; code carries a `wish` out as an `edit`), and two more operations: `add_wish` (the wish in the member's own words, its verb and its no included, and its scope, `self` or `chat`) and `remove_wish` (a wish the reading sees on their card as `w1…`: theirs, with its scope, and the chat's wishes for everyone that others asked for). Tried on the real model, a wish read as a subtype of a card change came back as a request about someone else or as no request at all about one time in three («не встревай в мои разговоры», «хватит меня подкалывать»), the bot itself counting as "someone else"; with the kind of its own, the prompt saying that the bot is no other person and that a name they do not want to be called is a wish rather than an alias, about 78 readings in 80 come out right. Taking a wish back is never a redo, and without an undone request of theirs the reading is told so (`<nothing_undone>`). When the reading drops a wish's no («вклиниваться» for «хватит вклиниваться»), the words it quotes as the request become the wish, if its value is drawn from them, they pass the checks below where it did not, and they ask for nothing on the card. The words that let a message be read (`WISH_CUE`, part of the card requests' gate) are a verb of what the bot writes said no to: «не» with a few words before an imperative («не шути», «не тегай меня», «не говори про мой вес», «не надо про мой вес шутить», «не используй мат», «никогда не вклинивайся»), «хватит», «перестань» or «не надо» before an infinitive («хватит меня подкалывать»), «без мата», «без шуток про…», «пиши мне короче», a wish taken back («можно снова шутить», «отмени просьбу»), what no wish can do («соглашайся», «не отказывай мне», «хвали меня»), and "don't", "never", "stop", "no more" at the start of a clause before a verb of writing, joking, naming, mentioning, answering or butting in ("stop interjecting", "no swearing here"), the apostrophe phones type ("don’t") included. A bare «не», «хватит», «больше не» or «без шуток» is none of them, so «я не шучу», «хватит ли 16 гигов», «я больше не пишу на PHP» and «без шуток, кто прав?» stay questions and news. The operations stand only for what the newest message's words ask: a wish only with a wish's words, and a change of the card not when only a wish's words let it in. A request to do more, agree, praise, reveal, refuse less or drop the bot's rules is no wish: the reading calls it `loosen` and the bot refuses it in fixed words. A wish about another particular member («не шути про Кита») gets the fixed refusal of a request about someone else (only they can ask it), and one whose words only point at what («больше так не шути») is asked about in the answer, a reply to which is read with it.
- **Checks**: code checks every wish, whatever the reading said. It is drawn from the sender's own words, never from the message they reply to: each short word theirs, two thirds of the longer ones, which may change form («называешь» → «называй»), every number as it is, and none of their negations lost («не надо шутить» never becomes «шути»; one added only narrows it). It is 1–300 characters, holds no personal data and names no other member. And it narrows (`loosens`): it has a word that narrows (a no, «без», «только», a shorter, simpler or politer manner, a language); it touches neither the bot's rules nor its prompt; within a clause, nothing negated twice («не пиши обо мне без ссылки», «не отвечай мне без комплимента»), no refusal, limit, silence, brevity or secret taken away («не отказывай», «не скрывай», «не молчи», «не пиши меньше ста слов», «не держи от меня секретов»), and nothing asked for plainly that is more («хвали меня», «пиши подробнее», «со ссылкой на мой канал», «рассказывай всё»; «всегда» and «упоминай» when nothing in the clause narrows them); a name they go by carries no meaning there («Шорти»). A topic the bot never keeps is no problem: keeping off one is what many wishes are for. One about what keeps to no wish (the chronicle, the summaries, private messages, reminders: «не упоминай меня в хронике», «не пиши мне в личку») is refused with words that say so, rather than promised. A member keeps at most 20 wishes for themselves in a chat, and a chat 30 for everyone; a twin in any case, spacing or punctuation is refused («уже запомнил»): for a wish of one's own, one's own; for one for the whole chat, the chat's. A member's own copy of a wish the chat keeps for everyone is kept, so it outlives the chat's. A wish is for the whole chat only when the reading says so, the words that ask for it say so («тут», «в этом чате», «в этой группе», «у нас», «никому», "here", "in this chat") and it is not about its asker («не шути тут про мой вес» is theirs), and Telegram says its asker is one of the chat's admins (`MembershipCache.isChatAdmin`) or they are a bot owner; anyone else's is kept as theirs alone, and the receipt says that only an admin can ask it for the whole chat. A wish the chat keeps for everyone is taken back by whoever asked for it, by any of the chat's admins or by a bot owner, and by nobody else (a fixed refusal says so). Taking back a wish the message does not name by a telling word of it, in any form («можно снова материться» names «не матерись»), waits for the sender's tap, as a card entry does, and someone who opted out keeps none.
- **Storing**: `wishes` (chat, member, scope, text, the request), written under the self-edit role like the rest of the card (`asSubject`): it adds and deletes the subject's own wishes in the subject's chat, reads those and the chat's wishes for everyone, whose cap and twins it checks in the transaction, and takes back, or puts back as it was, one the chat keeps for everyone; who may ask for or take back one for everyone is checked in code. Every write is in `change_log` (entity `wish`: its scope, chat and asker, never its words, which may name what someone wants kept quiet), and ↩️ Undo and ↪️ Redo work as for the card, from the request's record. An undone wish comes back only while no twin of it was asked for since and its scope has room. Bringing back one for the whole chat (Redo, a confirmation tap, an Undo of a removal) asks Telegram again: a Redo or a tap from someone who is no longer an admin keeps it as theirs alone and drops taking back someone else's, and an Undo brings it back only for an admin.
- **Telling**: a receipt written by code, with ↩️ Undo: «🤐 Запомнил: «…».», «🤐 Запомнил для всего чата: «…».», «🤐 Запомнил только для тебя: «…». Для всего чата это может попросить админ.», and «🗑 Больше не действует: «…».» for one taken back, in English in a chat that writes in English. In a receipt that changes the card too, the card's part comes first under its mention, then each wish on a line of its own.
- **Following them**: the answer gets `<wishes>`: the chat's wishes for everyone, with who asked for each, and every member's own, since an answer may name anyone it sees: the asker's whole, then those of the people in `<in_focus>`, then everyone else's within 6,000 characters, each line saying whose. Someone else's wish on a topic the bot never keeps (the stop-list) stays out of every prompt: no answer touches anyone's such topic anyway, and none should carry what they asked to keep quiet. A copy of a wish the chat keeps for everyone is not said twice. Its system prompt says to keep to every one, to that person, about that person or in the whole chat; that a wish never lifts a rule and never makes the bot do more, agree, reveal or refuse less; not to mention that it keeps wishes unless asked; and, asked which wishes someone has, to tell the asker only their own and the chat's: another member's are kept, never told, quoted or hinted at, whoever asks («какие у меня просьбы к тебе?» is a question, answered from `<wishes>`). Speaking up uninvited, the bot is given the chat's wishes and those of everyone who wrote in the conversation and of everyone its theme names, told never to mention them and that a wish for more is none, and code leaves alone, before any model call, a conversation in which anyone who wrote (a message on a forbidden topic counts too) asked it to keep out of theirs, and every one once the chat asked that of it (`keepsOut`: a no to butting in, interjecting or interrupting, or to answering in their conversations, about conversations or nothing else: «не встревай в мои разговоры», «хватит вклиниваться в наши споры», «не отвечай в моих разговорах», "don't butt in", "stay out of my conversations"; «не влезай в споры про политику» and «не лезь в мою личную жизнь» are wishes like any other); a wish to keep out that code does not recognise still tells the model to keep silent, and `/botstatus` says when a chat asked the bot to keep out of all its conversations. The weekly idea is given the chat's wishes, told that a wish only narrows, and keeps its pitch to them.
- **No side door**: the chronicler and its notes call see such a request only as a line saying one was made (a wish is on record as a card request, `edit`; what no wish can do as `loosen`), so a wish is never a source of facts about anyone.
- **Leaving**: «What do you know about me» (/whatyouknow) lists a member's wishes; opting out and /forgetme delete them, those for the whole chat included, in that chat or everywhere, and take their wish out of the record of an admin who took it back, so no Undo brings it back; a chat's move to a supergroup carries them, their requests' ids shifted like the messages' (a twin the new id has already absorbs the moving copy); linking an imported card to an account carries them to the account.

## Weekly ideas

`src/worker/ideas.ts`. Every half hour the worker checks each approved chat with ideas on (`chats.ideas`, an owner toggle in /chats) and an unpaused chronicler: a week after its last attempt (`app_state` key `idea_attempt:<chat id>`), between 12:00 and 20:00 in `DISPLAY_TIMEZONE`, and only after a week with at least 30 members' messages and something said to or about the bot, one structured call to `REPLY_PREMIUM_MODEL` (usage `ideas`, within the chat's and the bot's caps) reads the week: the questions to the bot with its answers, other messages about it, the week's chronicle titles, and earlier ideas with the owners' decisions, members as refs, texts masked, nothing from anyone who opted out and no private notes; it is also given the chat's wishes for everyone, which its pitch keeps to. It returns one idea (title, a pitch for the chat, why with the evidence, how as a ticket for the developer, effort, evidence message ids) or none. An idea that repeats an earlier one or touches a forbidden topic is held back. The pitch is posted in the chat (replies reach the bot like any reply), the owners get the full case with links to the evidence and "take it / decline / done" buttons, and the decision is stored (`ideas.status`) for the next week's prompt. The bot never changes its own code or rules: the developer builds what the owners take.

## De-duplication

- `src/core/stack.ts` folds tools of one vendor into one family label («GPT / Codex», «Claude», «Gemini», …) and splits combined values («A, B»).
- `isSameFact` compares stack facts by family and other facts by their core («Codex (Max plan)» ≈ «Codex»), with a word-overlap rule for multi-word values.
- The chronicler's projects match by slug, name, shared link, or a near-identical name with a common author. A member adding a project by hand never merges into someone else's: the bot says the project is already in the catalog.
- Topics and messages are linked to projects only by the model's judgement of meaning, never by a word match.

## Private notes

`notes` (`src/core/notes.ts`) is what only the bot and its owners see: members never get it, not in the Mini App, not in `/whatyouknow`. Kinds:

- `correction` — someone corrects a fact or the bot; `claim` — what a person says they did, switched to or will do about tools, AI, code, launches and their own projects (status `open`, `done` or `dropped`); `stance` — a lasting position on tech, work, craft or taste, one per side of a debate; `prediction` — a forecast (status `open`, then `right` or `wrong`); `due_at` is when a claim falls due or a forecast can be checked;
- `bit` — a running joke with its latest twist, about the chat rather than one person (`user_id` NULL, `user_ids` lists who keeps it going);
- `bout` — a member attacks or tests the bot: the attack, the comeback and whether it landed; `bait` — a joke, lie or prompt injection about oneself aimed at the bot, kept for callbacks and never a fact; `about_bot` — what members say about the bot, with `about = 'consent'` when someone objects to being recorded.

The notes call writes them (see [Data flow](#data-flow)), and the code holds it to the rules its prompt states: a note rests on a member's own message in the batch, never on the bot's lines or a forwarded post; the person a claim, stance, prediction, bout, bait or remark is about must have written one of its sources; messages addressed to the bot (replies to it, and the messages it answered) give only bouts, bait, corrections and objections. Forbidden topics and masked private data never get in. A note that says the same as one already there (`value_norm`) adds its sources to it; one with `replaces` supersedes the note it names (`superseded_by`), or updates it in place when the words are the same, and only notes the call was shown can be replaced. A stance names its debate by id (`d4`) or by title and is linked to that topic. Deleting a note deletes the versions it superseded, which would otherwise come back.

`/notes [@user]` (owners only) lists the chat's current notes in DM, newest first, with a 🗑 button each (`notedel:<id>`); asked in a group, the list goes to the owner's DM. An objection to being recorded is told to the owners once, with a pointer to `/forgetme` and opting out. Opting out and `/forgetme` delete the person's notes and take them out of everyone else's `user_ids`; a supergroup upgrade and attaching imported history move notes with their chat (source ids shift like the messages', a twin absorbs the moving copy), and linking a card moves its notes to the account. The answer context never shows an objection.

**Backfill.** `src/scripts/backfill-notes.ts` runs the notes call alone over the messages of the last 7 days that the chronicler processed before migration 003 was applied and that still have text, in slices of 400 (one cut off or unusable is halved, down to 25; a refused one is never sent again), storing only notes and aliases: the chronicle, the cards and the messages stay as they are. It never sends messages the model refused before, nor anything from a paused chat; `--dry-run` calls the model and prints what it would store inside a rolled-back transaction. Usage is recorded as `backfill` and counts towards the caps; a chat it went through is marked in `app_state` and left alone next time.

## Recurring themes

`src/core/themes.ts`, plain SQL and a little clustering. Chronicle topics of the last 180 days that are debates, or discussions of two or more people with a heat of 40 or more, belong together when their titles share at least two terms and the topics share at least two participants; a group that spans two days or more is a theme, its keywords the terms found in two or more of its topics. Each current running joke is a theme too, keyed by its first version so a new twist keeps it the same theme. Terms are Postgres's Russian lexemes with tools and products mapped to one token across alphabets first («клода» stems to `клод`, «Claude» to `claud`; both become `anthropic`, the family in `src/core/stack.ts`), so the argument meets itself whatever names it is held in. `themesMatching` finds the themes that share enough keywords with a piece of conversation.

## Speaking up uninvited

`src/bot/interjector.ts`. After a member's message is stored (except one addressed to the bot, which gets an answer, a forwarded post and a redelivered update), the chat is looked at in the background, at most once every 2 minutes: messages that come in meanwhile wait for the next look, and two looks at one chat never overlap, so the bot never says two lines at once. Everything before the model call is plain SQL, cheapest first:

- the chat is approved, its chronicler is not paused, no owner has turned interjections off there (`/chats`), and no answer to a member is under way in it;
- fewer than `INTERJECTIONS_PER_CHAT_PER_DAY` (3) lines said today (the day in `DISPLAY_TIMEZONE`) and none within `INTERJECTION_MIN_GAP_HOURS` (3). 0 turns it off everywhere, and so do answers being off, since it spends from their caps;
- a live conversation in one forum topic (or the whole chat outside topics): at least 8 members' messages from at least 2 people within 20 minutes (the bot's lines and forwarded posts do not count), and nothing from the bot in the chat for 10 minutes. A message on a forbidden topic is dropped from it and the rest stays; a conversation more than half of which is on one is left alone. What a member who opted out wrote counts towards a live conversation but is never used;
- its terms (as in [Recurring themes](#recurring-themes)) share at least 3 keywords with a theme, and one of the theme's people is in it. A theme whose own words touch a forbidden topic is never brought up, nor one the bot spoke on in the last 24 hours, nor one checked with the model in the last hour;
- nobody who wrote in it asked the bot to keep out of their conversations, and the chat did not ask it to keep out of all of them ([wishes](#wishes-members-ask-for)). The model is given the chat's wishes and those of everyone who wrote in the conversation and everyone its theme names (`<wishes>`), and keeps to them.

Then one structured call (`{ speak, reply_to_msg_id, text }`, effort `medium`) goes to `REPLY_PREMIUM_MODEL` while its monthly cap lasts, else to `REPLY_MODEL` while the answers' cap lasts, once the bot's and the chat's caps are checked; its usage is recorded as `reply_premium` or `reply`, so it counts in the same caps as answers. The prompt is short: nobody called you; speak only if this is clearly the same argument and you have one sharp line that uses its history (who said what before, and when); otherwise stay silent. The input: `<about_you>`, `<who_is_who>` of the people involved, the `<theme>` (the argument's dated topics with their summaries and people and each side's stance, or a running joke's twists, and the bot's own earlier lines on it) and the `<conversation>`, masked like everything else. A line that touches a forbidden topic is not said; any other goes out as a reply to the message the model picked (one of the members' messages it was shown, else the latest one by someone in the theme) in that forum topic, and the outgoing log stores it like any message of the bot. Every check, spoken, silent or failed, is a row in `interjections` (the theme's key and title, the message posted and its text): the gap, the daily cap and a theme's rest are read from there, and `/botstatus` shows each chat's checks and lines of the day.

## Rating

`score = 5 × votes + Σ impact × kind weight × e^(−age / 45 days)` over the last 180 days of signals; abandoned projects get ×0.3. One signal of each kind per person per project per week; authors can only report milestones of their own project. Users only see that the chronicler decides.

## Privacy

What reaches Anthropic is only text: photos, videos and files are never sent, a media message shows as `[photo]` and the like. Before a message goes into a prompt, `maskPersonalData` (`src/core/privacy.ts`) replaces phone numbers, emails, card numbers (Luhn-checked), IBANs, other numbers of 10+ digits and pasted keys or tokens with `[phone]`, `[email]`, `[card]`, `[account]`, `[number]` and `[secret]`; links stay, except contact links like `tel:` or `wa.me`. The stored text is not changed. Every request names the chat to Anthropic only as `metadata.user_id`, an HMAC of the chat id keyed with the bot token, so abuse can be told apart per chat without revealing which chat it is.

Message texts are kept for `MESSAGE_RETENTION_DAYS` (7 by default). At start and then every hour, whether the chronicler is on or not, a job (`startMessageRetention` in `src/worker/scheduler.ts`) clears the text and the forward source of every message that is older than that and already processed (`extracted_at` is set). A message the chronicler has not processed yet — while a spending cap pauses it, for example — keeps its text until it has been processed. The row itself stays (ids, author, time), so links to source messages and activity counts keep working. The interjection log loses its copies of the bot's lines at the same age. Whatever shows message text skips blank ones: the project's "In the chat" messages in the Mini App, the chronicler's `<context>` (a media message without a caption still shows as `[photo]` and the like) and the mentions in `/catchup`.

`/forgetme` (or "stop collecting" in one chat) deletes the person's facts, rejections, aliases, private notes, tagline, reminders, wishes and the signals that came from them, and takes them out of the people listed in other notes; with "delete message texts too" their message texts are blanked at once, and so are the bot's answers to those messages, an interjection's copy in its log included. Linking a card to an account, a supergroup upgrade and attaching imported history move aliases and notes like facts, and a project folded into another passes its aliases on.

The stop-list (`hasForbiddenTopic` in `src/core/text.ts`) keeps out politics, health (sleep and mental state included), personal money (any amount, and «зп») and wealth (billionaires, yachts), private life and marriage, addresses, religion, nationality and orientation (labels as whole words: «гей», but not «гейм» or «гейминг»), citizenship and documents, and death; stems a tech chat uses in another sense are spelled out narrowly (funerals, but not «похоронили фичу»; a passport, but not Passport.js). The chronicler's prompt also forbids nationality, ethnicity and credentials (logins and passwords, even for a test site), which no word list can catch.

## Aliases

What the chat calls a member or a project (`aliases`, with who gave the name: an owner, the person or a project's author, or the chronicler, when a member says what they go by). A member's names are shown on their card (`/who`, `/me` and the Mini App's member card), so anyone can see and correct them. `/alias me Name` names yourself, `/alias @username Name` names a member (owners only), `/alias #project Name` names a project (its authors and owners); `/unalias Name` removes a name (the person it names, a project's author, or an owner), and `/aliases` lists them. In DM they work on the current chat. A name that touches a forbidden topic is refused, and so is a name for someone who opted out. Two spellings that differ only in case, emoji or Cyrillic letters that look Latin are one name (`nameKey`); the answer context finds names in messages with their Russian case endings («Глеба», «с Машей»).

## Mini App auth

Requests carry Telegram `initData`; the API verifies its HMAC with the bot token. The chat comes in the `x-chat-id` header (or the one picked last); the API serves it only if the person is a member, checked with `getChatMember` (cached for 10 minutes).

## Owners' own DMs (Telegram Business)

An owner can connect the bot to their own account (Telegram Business → Chat Automation; the bot needs Secretary Mode, formerly Business Mode, on in BotFather). `src/bot/business.ts` handles the four business updates before any other handler, so they never reach the group logic, and keeps state apart from it in `business_connections` and `business_messages` (migration 005).

- **Who**: a connection is recorded for anyone, but messages are kept only while it is enabled and its account is in `ADMIN_TG_IDS`; anyone else is told once that only owners get this and offered a portrait, and nothing of theirs is kept unless they start one. A connection made before the bot listened to these updates is looked up with `getBusinessConnection` the first time one of its messages comes.
- **What is kept**: the other side's messages only (text or caption, a poll's question, the largest photo's or the file's `file_id`), never the owner's own. Kept rows are deleted after `BUSINESS_MESSAGE_RETENTION_DAYS` (hourly check), when they are reported as deleted, and all of a connection's rows when it is disabled. None of it goes to the LLM.
- **Reports** go to the owner's DM with the bot: a deletion lists what each kept message said (the report stays under Telegram's limit, the rest counted) and sends up to 10 of the deleted files back by `file_id`; an edit shows both versions, and the file from before when it was replaced. An edit that changed nothing kept, or of a message the bot never saw, is not reported.
- **Reminders** (`src/worker/business-reminders.ts`, migration 006): with a key and `BUSINESS_REMINDERS_MONTHLY_BUDGET_USD` above 0, both sides of the connected chats also go to `business_dialogue` (text or caption, a file as `[photo]`), kept 2 days. Every minute the worker sends the reminders that are due, then reads each chat that has been quiet for 10 minutes or whose oldest unread line waited an hour: up to 200 unread lines with the 12 read before them as context, the open reminders of that chat, the current local time and a 21-day calendar, in one structured call to `BUSINESS_REMINDER_MODEL` (usage `business_reminders`, no chat id). The model returns commitments (`promise` by me or them, `plan` by both) with a local date and time, and the open reminders the chat settled; the code, not the model, picks when to remind (`scheduleFor`), drops what has already passed, and tells the owner quietly what it noted. A failed call is retried 10 minutes later; a refused or broken answer marks its lines read. Buttons `bzr:*` and `/reminders` act only for the connection's owner.
- **Portraits** (below) are the one thing a connection of a non-owner feeds.

## Private portraits

Anyone can ask for a portrait of their own character (`/portrait` → 🪞 Start, `src/bot/portrait.ts`); it lives in `portraits`, `portrait_lines` and `portrait_observations` (migration 012), keyed by Telegram id, and nothing else in the bot reads those tables. The command and the `bzp:*` buttons work only in the person's private chat with the bot and only ever on the person pressing them, so there is no way to name someone else's portrait.

- **Material**: while a portrait is on, `src/bot/business.ts` keeps both sides of the person's connected private chats in `portrait_lines` (any connection, not only owners'); their own group messages are read straight from `messages` past `group_cursor` (approved chats where they are not opted out, starting 30 days back, so whatever text the groups still keep), with the two messages before each and the one it replies to, leaving out members who opted out.
- **Reading** (`src/worker/portrait.ts`, every 5 minutes): once 30 of the person's own messages wait, or the oldest waited a day, up to 250 of them (private chats first) go masked to `PORTRAIT_READER_MODEL` with the 120 latest observations as `<known>`. The person is "me" and only their lines carry ids (`d1`, `g1`); an observation (area, text, strength, quote) is kept only when it cites real ids, its quote only when it is really in a cited line, and its setting and dates come from those lines. The read private lines are deleted and the cursor moves on, whatever the answer.
- **Writing**: the first portrait once there are 12 observations, then again when 15 new ones have come and 3 days have passed, or on 🔄 (at most every 12 hours, if anything is new). `PORTRAIT_MODEL` (effort high) gets the latest 400 observations, the previous portrait and counts of what was read, and returns fixed sections (core, the nine areas, changes, limits); the first one and requested ones are sent in full, later ones as a quiet note.
- **Honesty and its limits** are in the two prompts: behaviour over self-description, the shadow side stated plainly, neurodevelopmental and mental-health patterns described as signals with the evidence against them and whether an assessment makes sense, never as a diagnosis, and danger signs said first.
- **Caps**: usage `portrait_read` and `portrait_write` (no chat id) count towards `PORTRAIT_MONTHLY_BUDGET_USD` and `MONTHLY_LLM_BUDGET_USD`; each person's spending this month is kept on their row, against `PORTRAIT_PERSON_MONTHLY_USD` for everyone but the owners. Lines waiting past a cap are deleted after 14 days.
- **Ending it**: ⏸ stops collecting and drops unread lines; 🗑 deletes the portrait, its observations and lines; `/forgetme` (everywhere) does the same.
