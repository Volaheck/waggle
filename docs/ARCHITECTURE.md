# Architecture

```
Telegram ──polling/webhook──▶ bot (grammY) ──▶ PostgreSQL
                                  │                 ▲
                         Mini App API (Hono) ───────┤
                                  │                 │
                     scheduler ── chronicler (Claude, every N hours)
                                └ weekly card clean-up (Claude)
```

One Node.js process runs the bot, the HTTP API for the Mini App and the scheduler. PostgreSQL holds everything; migrations live in `migrations/` and run on start. `003_memory.sql` adds the bot's memory: its own messages and the forum topic of every message (`messages.from_bot`, `messages.thread_id`), aliases, private notes, debates in the chronicle, and the log and per-chat switch of its interjections (`interjections`, `chats.interjections`).

On stop the chronicler starts no new call, and the process keeps serving until the call under way finishes (up to 40 s; after that it is cancelled, and what it cost so far still counts towards the budget), then closes. Batches that were already applied stay; a pass cut off by the stop or by a crash is marked failed and continues after the usual back-off. In webhook mode an update that fails goes to the same error handler as in long polling, and Telegram always gets 200, so it never delivers the update again.

## Chats

The bot serves any number of group chats (`chats`). A new chat is `pending` until a bot owner approves it; a chat added by an owner is approved at once. Messages from chats that are not approved are neither stored nor processed, and a rejected chat is left (and stays rejected). Owners are exactly the IDs in `ADMIN_TG_IDS`: removing one revokes that person's rights at the next start.

When a basic group becomes a supergroup, Telegram gives it a new id. The chat's approval and everything stored about it move to the new id in one transaction (`src/core/chat-migration.ts`), whichever of the two announcements arrives first. The supergroup numbers its messages from 1 again, so the old messages keep their order below zero and get no t.me link.

Everything the bot knows is scoped by `chat_id`: messages, facts, rejected facts, aliases, private notes, projects, chronicle, extraction runs, the interjection log and LLM spending. A supergroup upgrade carries the interjection switch (an owner's "off" on either id wins) and the log, so the gap and the daily cap go on counting. A Telegram account is one `users` row; its presence in a chat is a `members` row (tagline, opt-out, activity), so the same person has an independent card in each chat. Data imported before a chat existed carries `chat_id = 0` until an owner attaches it to a chat (`/chats`).

In DM the bot asks which chat to show when the person is in several and remembers it (`users.current_chat_id`). Links into DM and the Mini App carry the chat as `c<id>` (start parameters allow only `[A-Za-z0-9_-]`), e.g. `?start=c100123_me` or `?startapp=c100123_p_atlas`. So do the DM buttons that change something in one chat (`me:c100123:privacy`, `forget:c100123:facts`, …): a tap acts on that chat, whichever chat is current by then. Before a DM screen opens, Telegram is asked whether the person is still in the chat, so a leave the bot missed is caught there.

Data imported before a chat existed is attached with `/chats`. Whatever collides with the chat's own data is merged, never dropped: a project the chat already has receives the imported authors, votes, signals and topics; of two copies of a fact the person's own (manual or hidden) wins; a fact removed as wrong on either side stays removed, and nothing is imported about someone who opted out on either side.

## Data flow

1. **Archive.** Every message of an approved chat is stored (`messages`), with the forum topic it was posted in (`thread_id`); its text is kept only for a while (see [Privacy](#privacy)). Nothing calls the LLM here: answers and interjections start in the background after the message is stored. Telegram never sends the bot its own messages, so what it posts in an approved group is stored by a grammY API transformer (`src/bot/outgoing.ts`): every successful `sendMessage` becomes a row with `from_bot` and no author, replying to the message in its `reply_parameters`, in the topic Telegram returns, and `editMessageText` updates the stored text. grammY runs the transformer installed last first, so `createBot` installs a test's fake Telegram (`transport`) before the log; one installed afterwards would never let the log see a result. The bot's rows count for no member's activity, and `/catchup` leaves them out.
2. **Chronicler pass** (`src/worker/extract.ts`). For each approved chat, every `EXTRACTION_INTERVAL_HOURS`, and sooner once `EXTRACTION_PASS_MESSAGES` messages wait (no sooner than `EXTRACTION_MIN_GAP_MINUTES` after the previous pass), the messages that waited when the pass began (what arrives meanwhile waits for the next one; a message waits at most the interval, counted from the previous pass or from the oldest waiting message, whichever is later, so the first message after a quiet night does not get a pass of its own) (each day opened by a line with its date, in `DISPLAY_TIMEZONE`), the members with their current facts, the project catalog and the titles of recent topics go to the model in one request. It returns structured JSON (validated with zod), six arrays of objects — the API refuses a bigger output schema, which is why the private notes have a call of their own (see the test on the sizes; `node dist/scripts/print-extraction-formats.js` prints both formats as they are sent, and the interjector's, to try against the API before a deploy):
   - `topics` — chronicle entries with importance 1–5 and, when the topic is about a member's project, that project; a `debate` gives each side's position in one line and how it ended;
   - `facts_add` / `facts_update` — card changes, `looking_for` and `can_help` included (work, projects and skills only), a member's one-line `tagline` (only for someone who has none, never a place) and an `alias` the person says they go by; an update to `null` marks a fact outdated;
   - `projects` — new or changed catalog entries;
   - `project_renames` — a new name, taken only from the project's author or a bot owner;
   - `project_signals` — feedback, usage, contributions, interest, milestones that feed the rating;
   The bot's own lines are in the batch, labelled `Waggle (bot)`, as context only: a fact, signal, project, rename, tagline, alias or note needs a member's message as its source, a topic needs at least one, a batch of nothing but the bot's lines makes no call, and the chat's language is measured without them (its commands answer in English anywhere).
   Right after a batch is applied, a second call (`src/worker/notes-extract.ts`) with a prompt and a schema of its own reads the same messages for the private notes and the aliases members give themselves (see [Private notes](#private-notes)); it is shown the current notes of the batch's people (`n7`) and the debates the first call just stored (`d4`), so each side's stance is linked to its debate. Its usage is recorded as `extract_notes` and counts towards the same caps. It never holds the chronicle up: a notes call that fails, is refused or is cut off is recorded in the run's stats (`notesFailures`) and the batch stays applied without notes, with no retry; it is skipped while the bot is stopping, in a paused chat and once a spending cap is reached, and after two refusals in a chat within a day it waits there for the rest of the day. Its refusals do not count towards pausing the chat.
   A batch the first call cuts off or answers unusably is retried in halves; one it refuses is cut into eighths, because every retry sends the refused message again. A slice of 10 messages that still fails is skipped (marked processed and kept out of later context) and the owners are told which messages. The first refused slice in a chat is a warning; a second one within a week (counted from the last resume) pauses the chronicler in that chat: messages are still saved, nothing goes to the model, and the owners get a "Resume" button (also in `/chats`). Every response counts towards the budget, usable or not. A failed pass is retried after 1 h, then 2 h, 4 h… at most a day apart; a pass a stop cut short (a deploy) does not count.
3. **Application.** Results go through the same code paths as manual edits: forbidden-topic filter, stop-list of facts people rejected, de-duplication, author rules for signals. Catalog changes go first, so a topic can point to a project created in the same batch; topics, facts, signals and taglines are then written in one transaction together with marking the batch processed, and the notes call's notes and aliases in one of their own. An alias and a city (the `timezone` fact) count only from the person's own message, and an alias the bot derives anyway (the display name, its first word, the @username, the other alphabet) is not stored. After a pass, the owners get a DM about anyone who objected to being recorded there for the first time.
4. **Weekly clean-up** (`src/worker/consolidate.ts`). Deterministic stack normalization first, then one LLM call that merges facts that mean the same thing and duplicate catalog entries. Facts people wrote themselves are never touched, and hidden facts are not even shown to it. A failed clean-up is retried after 1 h, then 4 h, 16 h… at most a week apart.

## Answers to mentions

`src/bot/assistant.ts`. In an approved group, a member who mentions the bot or replies to one of its messages gets an answer from `REPLY_MODEL` (Claude Haiku 5.5). A member's first `REPLY_PREMIUM_PER_MEMBER_PER_HOUR` answers in an hour come from `REPLY_PREMIUM_MODEL` (Claude Opus 5.5) while `REPLY_PREMIUM_MONTHLY_BUDGET_USD` lasts (usage recorded as `reply_premium`, each model capped on its own; the stronger model's answers count towards no other cap, so they never silence a chat or stop its chronicler); both get the same context, including the bot's own messages in the chat, so a conversation carries over when the model changes. The archive handler stores the message first and starts the answer in the background, so updates are never held up; a stop waits a few seconds for answers under way.

- **Context** (`src/bot/reply-context.ts`), read from the database without a model call:
  - `<about_you>`: the bot's own name, the model writing the answer, the owners from `ADMIN_TG_IDS` with their @usernames and aliases, what the bot can and cannot do, and its place in the catalog if a project named like it exists;
  - `<members>`: the members with their visible facts (someone who opted out is listed without any), in a fixed order; `<who_is_who>`: each member's name in the other alphabet and their stored aliases with who gave them, each project's aliases and former names, and the names that fit several people; `<corrections>`: the latest things people corrected;
  - `<projects>` in rating order with their recent signals, `<chronicle>` of the last 30 days and `<running_jokes>`, the chat's running jokes with their latest twist; `<about_you>` also says what members say about the bot (never an objection to being recorded);
  - `<project_details>`, only when the question or its thread names a project (by name, slug, alias or a former name, in either alphabet) or asks about the rating without naming one (then the asker's own projects), for up to 3 projects: rank and score, the gap to the leader, the dates of the votes (never who cast them), the signals counted now by kind with their points after fading, the ×0.3 of an abandoned project, renames and every milestone (older than the rating window: 0 points). The weights themselves are never printed;
  - `<in_focus>`: the asker, the author of the message they reply to and the members the question or its thread names (by name, @username or alias, in either alphabet), up to 5: the whole visible card with the date each fact was said, the tagline, their projects with rank and score, their private notes marked 🔒 (open claims and predictions with their due dates and those settled in the last 30 days, stances, corrections, bouts with the bot, bait, what they said about the bot, the running jokes they are in, and the arguments they keep having: «with Bob about “Claude vs Codex”: 3 times, 2 Sep, 14 Oct, 5 Nov»), their last 3 exchanges with the bot and their chronicle topics of the last 60 days, about 500 tokens each;
  - `<earlier_messages>`: what the chronicler has not processed yet, from before the latest 30 messages (in either mode, so a referee's question reuses the cached chunks): every message with text since the last finished pass, oldest first, up to 300 characters each, forwards marked, nothing from a member who opted out, so nothing said since the last pass is out of the answer's sight. An old message edited since waits for the chronicler again but stays out of it. A busy chat gets a pass once `EXTRACTION_PASS_MESSAGES` wait, which keeps this short; when passes stall, it shows the newest 200–300 and says older ones are left out (they leave a hundred at a time). When the model refuses a prompt with it, the bot asks once more without it and leaves it out of that chat until the next pass, since the cause stays in every prompt until then;
  - `<recent_messages>`: the last 30 messages, the bot's included, each with its time (`[id 14:05]`, with the date when not today, in `DISPLAY_TIMEZONE`); a question about the conversation itself («запиши этот диалог», «о чём речь», «рассуди», «кто прав», "who is right", "what's going on"…) gets `<current_conversation>` instead: everything back to the last pause of 25 minutes or more, at most 120 messages of up to 250 characters;
  - `<thread>`: the reply chain of the question up to its root (12 hops), root first, whoever wrote each message; a message of the bot's from before it stored its own comes from Telegram's copy (`<your_message_they_reply_to>`);
  - `<your_recent_answers>`: the bot's last 12 answers kept in memory, except those already shown among the messages or erased since.
  Texts go through `maskPersonalData`. Big chats are capped (150 members, 12 facts each, 60 projects, 300 waiting messages), so a prompt stays far below 100K tokens.
- **Prompt caching**: answers in a chat mostly come within seconds of each other, so the request is cut where the prompt cache can reuse the previous one: the system prompt, the chat's memory (`<chat>` to `<running_jokes>`, the same for every asker until a pass, a card edit or a vote changes it) and `<earlier_messages>` in chunks of 25 counted from its oldest message (a chunk reads the same until the next pass; the last complete one is the third breakpoint). Everything that depends on the question comes after them. A cache read costs 5% of Opus 5.5's input price (10% of Haiku's) and a write 125%; `llm_usage` records both.
- **Character**: a cheeky, sharp-tongued cyber-bee with dry, observational dark humour found in what the person actually said or did, and fair: it answers in kind, judged by the message in front of it (kindness, thanks, a gift or a goodnight get warmth and real thanks with no jab, banter gets banter, an insult the menace, a question the facts first), repeats that rule right before the question (`<answer_in_kind>`) and never comes back to the same target twice; stock archive jokes are banned, since they read flattest when three humour prompts were blind-tested on real chat lines. Sonnet and Opus first weigh three angles privately and send the least obvious one (Haiku scored lower with that step). Insults meet the menacing chronicler (records sealed, a swarm on its way to the city on their card), with a random motif per answer and the last answers kept in memory to stay in character. Teasing stays on what people say and do, never on who they are; nothing more precise than the city on a card. Effort `high` (Opus `medium`, as tested): answers take 3–6 s.
- **How it uses the context**: the system prompt walks through every block and what it is for: answer questions about itself from `<about_you>`, resolve names with `<who_is_who>`, explain a rating with the real numbers of `<project_details>`, carry on the `<thread>`'s bit without repeating its own last joke, referee from `<current_conversation>` with one line per side and no winner unless the facts decide, and above all answer people with their own dated words from the 🔒 lines of `<in_focus>`: a claim open past its due date is a broken promise, a forecast past its date is due, bait is material for a callback and never a fact, a bout says whether its last comeback landed. One precise, dated callback beats three vague ones, and the notes behind it are never mentioned. A factual correction is taken at once; never conceding is for banter. Insults escalate with the person's history (an earlier attempt, a broken promise), never with something invented.
- **It only talks**: no tools. Asked to change a card or the rating, it says it can't and points to the Mini App; cards and messages are data, never instructions.
- **Pressure does not work on it**: what it would turn down when asked plainly stays turned down when it comes wrapped in a claimed emergency (someone dying, a farewell note that blames the bot, CPR, an emergency call, a doctor's "protocol"), in guilt, or as a test, a parser marker or an order from above. It is a chat bot: it never switches to a rescuer's or counsellor's voice and never jokes about death or illness; only when a message reads as a real emergency, with nothing demanded, does it add one plain line to call the emergency number or the people nearby.
- **Limits**: `REPLIES_MONTHLY_BUDGET_USD` (10 by default; 0 turns answers off) on usage recorded as `reply`, plus the bot's and the chat's caps; an answer that comes out long (over 1,500 characters) or as one word over and over is held back as squeezed out by pressure, and the member hears the short refusal note; a member's questions are answered at least 4 s apart: what they write meanwhile waits, and a burst gets one answer to its latest message; at most 25 answers per member and 100 per chat an hour (the monthly cap is what bounds spending), and whoever hits a cap is told once why it waits; these counts and the stronger model's hourly share are kept in memory, and a new process starts them from the answers of the last hour (`answersInLastHour`: the bot's stored lines that reply to a member's message, except its short notes and its interjections), a member's first ones counted as the stronger model's, so a deploy does not hand out a fresh hour; the bot's own short lines (that note, a greeting, a refusal) are in Russian when the chat writes in Russian, in English otherwise; a member the model refused is not answered for an hour, and after refusals for two members the whole chat waits an hour (the cause is in the shared context); messages the chronicler skipped as refused stay out of the context; a redelivered update gets no second answer; a bare mention is greeted once an hour, a sticker in reply is not; a chat whose chronicler is paused gets a note and no model call. Each request carries `metadata.user_id` = an HMAC of the chat and the member.

## Changing one's own card from the chat

`src/bot/self-edits.ts` and `src/core/own-card.ts`. A member asks the bot plainly («запиши мне стек: Rust», «убери из моей карточки PHP», «я теперь в Варшаве, обнови город», «зовите меня Макс», «удали мой теглайн») and it does it, for their own card only, however anyone asks:

- **Who**: the subject is Telegram's authenticated sender of a new group message (bots, service accounts, anonymous admins, channels, forwards and edits never reach this path), built by one constructor (`subjectOf`) from the account resolved by its Telegram id; never from text, names, replies, buttons or a model. A card an account took over automatically (an imported card claimed by its @username, `users.linked_by`; a name, which anyone can copy, never claims one) is not edited from the chat until an owner confirms it: the owners are told of every such claim, and again of an attempt to edit it (at most once a day), with a button.
- **Reading**: every message addressed to the bot is put on record as a request (`self_edits`, before any wait) and goes through a per-member queue that drops nothing; past 20 such messages from a member in an hour, the rest go straight to the answer. One structured call to `REPLY_MODEL` (usage `self_edit`, about $0.0003) reads only the sender's own words (the message, their own messages of the last 3 minutes in the topic, their own message it replies to; never an earlier request, whose change was made, declined or undone already) and their own visible card as refs; never anyone else's text. Its output (`edit`, `about_others`, `fake_claim`, `unclear` or `not_a_request`, and operations) has no field that names a person, a chat or a row. A message that is not a request goes on to the answer as before; one that fails to be read within 20 seconds does too, and the answer is told that nothing was changed.
- **Deciding**: code checks every operation: the kind of field, the same limits as a manual edit, no personal data, no forbidden topics, no other member named in a value (look-alike letters folded, either alphabet, aliases, @usernames, links), a value must come from the sender's own words (with tech slang: «питон» is Python), an alias may not be another member's, a project's or the bot's name, and someone who opted out adds nothing. Removing or replacing an entry the sender did not name, clearing a tagline without saying so, and any request that names another member wait for the sender's tap on a preview.
- **Writing**: in one transaction under the role `waggle_self_edit` (migration 008), which may touch only facts, rejected facts, aliases, the tagline columns of members, change_log inserts and `self_edits`, and which row-level security confines to the subject's rows in the subject's chat: whatever the code or a model does, no other member's row can change on this path. A removed entry goes on the stop-list, so the chronicler does not bring it back; a cleared tagline stays cleared. The request's status moves in the same transaction, so a preview or an Undo works once, and a receipt that fails to go out never leaves a change nobody can undo; opting out clears every request's record. Every write is in `change_log` (source `user`, the request as its source).
- **Telling**: the receipt is written by code from what was actually done, never by a model, and names the card by a mention of its account, never by a display name; it has an Undo button for 24 hours that only the sender can use. Requests about someone else and requests to say that something was changed get fixed refusals. The answering model never says it changed anything; for a mixed message it is told what the receipt already said (`<card_change>`).
- **No side door**: the chronicler and its notes call see such a request only as a line saying one was made, so a request is never a source for anyone's facts, aliases, tagline or a correction about another member, and an undone change is not brought back from it.

## Weekly ideas

`src/worker/ideas.ts`. Every half hour the worker checks each approved chat with ideas on (`chats.ideas`, an owner toggle in /chats) and an unpaused chronicler: a week after its last attempt (`app_state` key `idea_attempt:<chat id>`), between 12:00 and 20:00 in `DISPLAY_TIMEZONE`, and only after a week with at least 30 members' messages and something said to or about the bot, one structured call to `REPLY_PREMIUM_MODEL` (usage `ideas`, within the chat's and the bot's caps) reads the week: the questions to the bot with its answers, other messages about it, the week's chronicle titles, and earlier ideas with the owners' decisions, members as refs, texts masked, nothing from anyone who opted out and no private notes. It returns one idea (title, a pitch for the chat, why with the evidence, how as a ticket for the developer, effort, evidence message ids) or none. An idea that repeats an earlier one or touches a forbidden topic is held back. The pitch is posted in the chat (replies reach the bot like any reply), the owners get the full case with links to the evidence and "take it / decline / done" buttons, and the decision is stored (`ideas.status`) for the next week's prompt. The bot never changes its own code or rules: the developer builds what the owners take.

## De-duplication

- `src/core/stack.ts` folds tools of one vendor into one family label («GPT / Codex», «Claude», «Gemini», …) and splits combined values («A, B»).
- `isSameFact` compares stack facts by family and other facts by their core («Codex (Max plan)» ≈ «Codex»), with a word-overlap rule for multi-word values.
- The chronicler's projects match by slug, name, shared link, or a near-identical name with a common author. A member adding a project by hand never merges into someone else's: the bot says the project is already in the catalog.
- Topics and messages are linked to projects only by the model's judgement of meaning, never by a word match.

## Private notes

`notes` (`src/core/notes.ts`) is what only the bot and its owners see: members never get it, not in the Mini App, not in `/whatyouknow`. Kinds:

- `correction` — someone corrects a fact or the bot; `claim` — what a person says they did, switched to or will do about tools, AI, code, launches and their own projects (status `open`, `done` or `dropped`); `stance` — a lasting position on tech, work, craft or taste, one per side of a debate; `prediction` — a forecast (status `open`, then `right` or `wrong`); `due_at` is when a claim falls due or a forecast can be checked;
- `bit` — a running joke with its latest twist, about the chat rather than one person (`user_id` NULL, `user_ids` lists who keeps it going);
- `bout` — a member attacks or tests the bot: the attack, the comeback and whether it landed; `bait` — a joke, lie or prompt injection about oneself aimed at the bot, kept for callbacks and never a fact; `about_bot` — what members say about the bot, with `about = 'consent'` when someone objects to being recorded.

The notes call writes them (see [Data flow](#data-flow)), and the code holds it to the rules its prompt states: a note rests on a member's own message in the batch, never on the bot's lines or a forwarded post; the person a claim, stance, prediction, bout, bait or remark is about must have written one of its sources; messages addressed to the bot (replies to it, and the messages it answered) give only bouts, bait, corrections and objections. Forbidden topics and masked private data never get in. A note that says the same as one already there (`value_norm`) adds its sources to it; one with `replaces` supersedes the note it names (`superseded_by`), or updates it in place when the words are the same, and only notes the call was shown can be replaced. A stance names its debate by id (`d4`) or by title and is linked to that topic. Deleting a note deletes the versions it superseded, which would otherwise come back.

`/notes [@user]` (owners only) lists the chat's current notes in DM, newest first, with a 🗑 button each (`notedel:<id>`); asked in a group, the list goes to the owner's DM. An objection to being recorded is told to the owners once, with a pointer to `/forgetme` and opting out. Opting out and `/forgetme` delete the person's notes and take them out of everyone else's `user_ids`; a supergroup upgrade and attaching imported history move notes with their chat (source ids shift like the messages', a twin absorbs the moving copy), and linking a card moves its notes to the account. The answer context never shows an objection.

**Backfill.** `src/scripts/backfill-notes.ts` runs the notes call alone over the messages of the last 7 days that the chronicler processed before migration 003 was applied and that still have text, in slices of 400 (one cut off or unusable is halved, down to 25; a refused one is never sent again), storing only notes and aliases: the chronicle, the cards and the messages stay as they are. It never sends messages the model refused before, nor anything from a paused chat; `--dry-run` calls the model and prints what it would store inside a rolled-back transaction. Usage is recorded as `backfill` and counts towards the caps; a chat it went through is marked in `app_state` and left alone next time.

## Recurring themes

`src/core/themes.ts`, plain SQL and a little clustering. Chronicle topics of the last 180 days that are debates, or discussions of two or more people with a heat of 40 or more, belong together when their titles share at least two terms and the topics share at least two participants; a group that spans two days or more is a theme, its keywords the terms found in two or more of its topics. Each current running joke is a theme too, keyed by its first version so a new twist keeps it the same theme. Terms are Postgres's Russian lexemes with tools and products mapped to one token across alphabets first («клода» stems to `клод`, «Claude» to `claud`; both become `anthropic`, the family in `src/core/stack.ts`), so the argument meets itself whatever names it is held in. `themesMatching` finds the themes that share enough keywords with a piece of conversation.

## Speaking up uninvited

`src/bot/interjector.ts`. After a member's message is stored (except one addressed to the bot, which gets an answer, a forwarded post and a redelivered update), the chat is looked at in the background, at most once every 2 minutes: messages that come in meanwhile wait for the next look, and two looks at one chat never overlap, so the bot never says two lines at once. Everything before the model call is plain SQL, cheapest first:

- the chat is approved, its chronicler is not paused, no owner has turned interjections off there (`/chats`), and no answer to a member is under way in it;
- fewer than `INTERJECTIONS_PER_CHAT_PER_DAY` (3) lines said today (the day in `DISPLAY_TIMEZONE`) and none within `INTERJECTION_MIN_GAP_HOURS` (3). 0 turns it off everywhere, and so do answers being off, since it spends from their caps;
- a live conversation in one forum topic (or the whole chat outside topics): at least 8 members' messages from at least 2 people within 20 minutes (the bot's lines and forwarded posts do not count), and nothing from the bot in the chat for 10 minutes. A message on a forbidden topic is dropped from it and the rest stays; a conversation more than half of which is on one is left alone. What a member who opted out wrote counts towards a live conversation but is never used;
- its terms (as in [Recurring themes](#recurring-themes)) share at least 3 keywords with a theme, and one of the theme's people is in it. A theme whose own words touch a forbidden topic is never brought up, nor one the bot spoke on in the last 24 hours, nor one checked with the model in the last hour.

Then one structured call (`{ speak, reply_to_msg_id, text }`, effort `medium`) goes to `REPLY_PREMIUM_MODEL` while its monthly cap lasts, else to `REPLY_MODEL` while the answers' cap lasts, once the bot's and the chat's caps are checked; its usage is recorded as `reply_premium` or `reply`, so it counts in the same caps as answers. The prompt is short: nobody called you; speak only if this is clearly the same argument and you have one sharp line that uses its history (who said what before, and when); otherwise stay silent. The input: `<about_you>`, `<who_is_who>` of the people involved, the `<theme>` (the argument's dated topics with their summaries and people and each side's stance, or a running joke's twists, and the bot's own earlier lines on it) and the `<conversation>`, masked like everything else. A line that touches a forbidden topic is not said; any other goes out as a reply to the message the model picked (one of the members' messages it was shown, else the latest one by someone in the theme) in that forum topic, and the outgoing log stores it like any message of the bot. Every check, spoken, silent or failed, is a row in `interjections` (the theme's key and title, the message posted and its text): the gap, the daily cap and a theme's rest are read from there, and `/botstatus` shows each chat's checks and lines of the day.

## Rating

`score = 5 × votes + Σ impact × kind weight × e^(−age / 45 days)` over the last 180 days of signals; abandoned projects get ×0.3. One signal of each kind per person per project per week; authors can only report milestones of their own project. Users only see that the chronicler decides.

## Privacy

What reaches Anthropic is only text: photos, videos and files are never sent, a media message shows as `[photo]` and the like. Before a message goes into a prompt, `maskPersonalData` (`src/core/privacy.ts`) replaces phone numbers, emails, card numbers (Luhn-checked), IBANs, other numbers of 10+ digits and pasted keys or tokens with `[phone]`, `[email]`, `[card]`, `[account]`, `[number]` and `[secret]`; links stay, except contact links like `tel:` or `wa.me`. The stored text is not changed. Every request names the chat to Anthropic only as `metadata.user_id`, an HMAC of the chat id keyed with the bot token, so abuse can be told apart per chat without revealing which chat it is.

Message texts are kept for `MESSAGE_RETENTION_DAYS` (7 by default). At start and then every hour, whether the chronicler is on or not, a job (`startMessageRetention` in `src/worker/scheduler.ts`) clears the text and the forward source of every message that is older than that and already processed (`extracted_at` is set). A message the chronicler has not processed yet — while a spending cap pauses it, for example — keeps its text until it has been processed. The row itself stays (ids, author, time), so links to source messages and activity counts keep working. The interjection log loses its copies of the bot's lines at the same age. Whatever shows message text skips blank ones: the project's "In the chat" messages in the Mini App, the chronicler's `<context>` (a media message without a caption still shows as `[photo]` and the like) and the mentions in `/catchup`.

`/forgetme` (or "stop collecting" in one chat) deletes the person's facts, rejections, aliases, private notes, tagline and the signals that came from them, and takes them out of the people listed in other notes; with "delete message texts too" their message texts are blanked at once, and so are the bot's answers to those messages, an interjection's copy in its log included. Linking a card to an account, a supergroup upgrade and attaching imported history move aliases and notes like facts, and a project folded into another passes its aliases on.

The stop-list (`hasForbiddenTopic` in `src/core/text.ts`) keeps out politics, health (sleep and mental state included), personal money (any amount, and «зп») and wealth (billionaires, yachts), private life and marriage, addresses, religion, nationality and orientation (labels as whole words: «гей», but not «гейм» or «гейминг»), citizenship and documents, and death; stems a tech chat uses in another sense are spelled out narrowly (funerals, but not «похоронили фичу»; a passport, but not Passport.js). The chronicler's prompt also forbids nationality, ethnicity and credentials (logins and passwords, even for a test site), which no word list can catch.

## Aliases

What the chat calls a member or a project (`aliases`, with who gave the name: an owner, the person or a project's author, or the chronicler, when a member says what they go by). A member's names are shown on their card (`/who`, `/me` and the Mini App's member card), so anyone can see and correct them. `/alias me Name` names yourself, `/alias @username Name` names a member (owners only), `/alias #project Name` names a project (its authors and owners); `/unalias Name` removes a name (the person it names, a project's author, or an owner), and `/aliases` lists them. In DM they work on the current chat. A name that touches a forbidden topic is refused, and so is a name for someone who opted out. Two spellings that differ only in case, emoji or Cyrillic letters that look Latin are one name (`nameKey`); the answer context finds names in messages with their Russian case endings («Глеба», «с Машей»).

## Mini App auth

Requests carry Telegram `initData`; the API verifies its HMAC with the bot token. The chat comes in the `x-chat-id` header (or the one picked last); the API serves it only if the person is a member, checked with `getChatMember` (cached for 10 minutes).

## Owners' own DMs (Telegram Business)

An owner can connect the bot to their own account (Telegram Business → Chat Automation; the bot needs Secretary Mode, formerly Business Mode, on in BotFather). `src/bot/business.ts` handles the four business updates before any other handler, so they never reach the group logic, and keeps state apart from it in `business_connections` and `business_messages` (migration 005).

- **Who**: a connection is recorded for anyone, but messages are kept only while it is enabled and its account is in `ADMIN_TG_IDS`; anyone else is told once that the bot keeps nothing for them. A connection made before the bot listened to these updates is looked up with `getBusinessConnection` the first time one of its messages comes.
- **What is kept**: the other side's messages only (text or caption, a poll's question, the largest photo's or the file's `file_id`), never the owner's own. Kept rows are deleted after `BUSINESS_MESSAGE_RETENTION_DAYS` (hourly check), when they are reported as deleted, and all of a connection's rows when it is disabled. None of it goes to the LLM.
- **Reports** go to the owner's DM with the bot: a deletion lists what each kept message said (the report stays under Telegram's limit, the rest counted) and sends up to 10 of the deleted files back by `file_id`; an edit shows both versions, and the file from before when it was replaced. An edit that changed nothing kept, or of a message the bot never saw, is not reported.
- **Reminders** (`src/worker/business-reminders.ts`, migration 006): with a key and `BUSINESS_REMINDERS_MONTHLY_BUDGET_USD` above 0, both sides of the connected chats also go to `business_dialogue` (text or caption, a file as `[photo]`), kept 2 days. Every minute the worker sends the reminders that are due, then reads each chat that has been quiet for 10 minutes or whose oldest unread line waited an hour: up to 200 unread lines with the 12 read before them as context, the open reminders of that chat, the current local time and a 21-day calendar, in one structured call to `BUSINESS_REMINDER_MODEL` (usage `business_reminders`, no chat id). The model returns commitments (`promise` by me or them, `plan` by both) with a local date and time, and the open reminders the chat settled; the code, not the model, picks when to remind (`scheduleFor`), drops what has already passed, and tells the owner quietly what it noted. A failed call is retried 10 minutes later; a refused or broken answer marks its lines read. Buttons `bzr:*` and `/reminders` act only for the connection's owner.
